# Protected Registered remote proposal

This source batch adds only the native proposal boundary. It has not been
compiled or run. It does not persist catalogue Installing, stage history, copy
rows, finalize an Image, publish Ready or serve an application request.

The SAME retained Registered host attempt owns the actual A lease and a
`NativeRegisteredRemoteProposalPublication` before transaction assignment.
Every call obtains a fresh actual target role/OWN and authenticated frame from
the SAME owned MF Arc. It builds that request from the retained A permit;
`source_capture_freeze(N)` is never used after transfer.

An original-hook/admission/native-journal `NativeRegisteredRemoteAttemptScope`
checks actual A custody, the original DB birth/open, no INITIAL ranges, original
no-writer registration and policy absence. It is distinct from NoDomain. The
actual native safety, UID/schema pins, protected MStore point and exact CLOSED
raw/catalogue preimage remain mandatory. MStore checks occur outside engine
guards. Inside the scope, point checks use the held original hook and native
journal without acquiring either again. A before-scope control boundary permits
real hook/caller revocation without deadlocking the held hook reader.

The native record binds the full actual source manifest, including its checksum,
R/H0/H, native receipt and actual OLD closures. It also binds exact bounded
canonical intent bytes/hash, target birth/open/Store/catalogue/namespace IDs,
metadata provenance and original native/raw safety hashes. Missing target native
indices stay `None`. The scoped DB watermark is observed before the put; it is
not an inferred native range floor.

The local sticky `native_registered_remote_proposal_v1` reader-refusal flag is
persisted with file and directory sync before the first native put. Every
continuation repeats that persistence, including when a previous failed
post-rename directory sync left the flag visible. Visible flag presence does
not establish its durability. It is excluded from portable schema-reader
features. Actual older-binary compatibility has not been tested for this flag.

At page transaction assignment, the publication retains the exact xid and
checksummed bytes BEFORE its first put. CURRENT and immutable archive are
written in that one native transaction. An actual successful commit return xid
is retained before every later check. A post-commit canceled response therefore
retains known native success even if readback/publication has not completed.

Fresh same-attempt reconciliation compares the original attempted bytes/xid
against exact CURRENT plus archive, checks the real page transaction is committed,
and verifies current actual point constraints. It does not rewrite the record or
reconstruct NoDomain after a proposal exists. Native inventory must contain only
the original four Registered records and this exact attempt's CURRENT/archive;
unknown or conflicting history fails closed.

A commit/fsync error preserves the attempted xid/bytes and durability health
fencing. Visibility, a remembered counter or an absent record does not establish
success. Unproven attempts remain unavailable; this batch does not automatically
reset them, select a new xid or create a new birth. Cold reconstruction and an
untouched-abort recovery path remain separate work.

`NativeRegisteredRemoteProposalReceipt` is actual protected-record evidence only.
Its reader requires the actual A scope and Store, full native identity and exact
committed readback. A pointer DTO cannot construct a receipt or authorize catalogue
or row writes. The separate catalogue sink must consume the actual receipt and
independently current role/OWN/lease/point; it cannot substitute local lineage or
ordinary writer persistence.

Source selectors `native_registered_fifth_remote_proposal_` use the real fifth
and actual authenticated source: successful native CURRENT/archive, cancellation
after native WAL followed by fresh same-xid reconciliation, caller revocation
before WAL and original hook ABA before WAL. They preserve user rows, raw state,
UIDs, native range points and the other range; full native-inventory hashes allow
only this proposal's two records to change. These tests have not run. A successful
post-WAL cancellation test is not a simulated fsync failure or physical recovery
qualification. Catalogue Installing, rows, power-loss recovery, populated Assigned
second-range movement and physical capacity qualification remain open.

The follow-up after source `d16e9319d` closes a visible-reader-flag retry gap.
It uses the existing atomic-replacement I/O fault seam at
`registered_remote_proposal.format.dir_sync`, after actual file sync and rename,
to return injected EIO before directory sync. The fifth-node source regression
`native_registered_fifth_remote_proposal_actual_reader_flag_dir_sync_failure_retry`
checks two fresh failing requests with a visible flag, no native xid and no
native-record changes. After removal of the fault, a fresh request may persist
the flag and publish the proposal. A later injected directory-sync failure must
also refuse a Verified continuation; successful retry keeps the original
proposal xid and bytes. This follow-up has not been compiled or run. Earlier
revision results do not cover it. This injected boundary test is separate from
native-page commit/fsync uncertainty, simulated power loss and physical hardware
qualification, none of which it establishes.
