# Oracle application preview profile

`oracle-preview-v1` is a separate, experimental Oracle SQL profile for application
migration development. It uses PostgreSQL drivers and native wire types. It is
not an Oracle certification or a completed iDempiere integration. The bounded
[`oracle-hr-v1`](oracle-hr-profile.md) contract remains separate.

Provision an empty standalone database with the CLI:

```sh
bicdb serve /tmp/bicdb-oracle-preview --port 5441 --sql-profile oracle-preview-v1
```

Connect with the standard PostgreSQL startup option
`options='-c bicdb.sql_profile=oracle-preview-v1'`. The server confirms the profile
in `bicdb_sql_profile` ParameterStatus. Its durable marker prevents reopening as
PostgreSQL or as the HR profile. Every connection must select the matching
profile. Existing populated databases cannot be converted with a serve flag;
connection-level SQL cannot switch the profile. Native transaction, authorization,
wire encoding and error contracts apply. Cluster mode is not qualified here.

The preview adds logical application-schema support to the HR front end:

- Schema-qualified tables and PostgreSQL COPY transport.
- Initial CONNECT BY hierarchy and LEVEL generator support, including PRIOR,
  NOCYCLE and ORDER SIBLINGS BY; see the hierarchy execution contract below.
- `CLOB` mapped to native `text`, `BLOB` to native `bytea`.
- Durable BYTE/CHAR length units and STANDARD byte capacity for new
  `VARCHAR2`/`CHAR` columns; see the character-column contract below.
- Native JSON validity predicates in CHECK constraints and `OCTET_LENGTH` for
  explicit RAW byte-length guards generated by the migration tool.
- Trailing table `CACHE`/`NOCACHE` hints removed as a declared native-storage
  adaptation; enabled constraints retain native enforcement. Disabled constraints
  fail rather than silently disappearing.

## Application schemas and row locks

The preview binds an unqualified application relation to the selected application
schema before parameter inference and execution. PostgreSQL JDBC's
`currentSchema` startup parameter and PostgreSQL startup `search_path` options
supply that selection. Quoted names retain their case; unquoted application
schema names follow Oracle uppercase folding. The first existing namespace in
the supplied list selects one current application schema; this does not implement
PostgreSQL's full relation-by-relation search-path fallback in Oracle mode.
An explicitly missing schema is preserved so table lookup fails there. An empty
selection is rejected. Without an explicit selection, an existing uppercase
username schema is used, otherwise the bootstrap public namespace is retained.
Provision the application namespace before connecting.

CTE names remain local query names. Qualified relations retain their explicit
namespace. Simple queries, prepared statements and COPY use the same binding;
prepared SQL retains the namespace resolved during Parse. Schema selection does
not grant table privileges. The bounded HR profile retains its public-namespace
contract; native PostgreSQL relation resolution is unchanged by this front end.

Text-format PostgreSQL binds retain the resolved character type. Numeric-looking
text and varchar values such as `001`, `1e2` and ` 1 ` remain strings for indexed
lookups and projections. Declared and inferred character types use the same rule
in the PostgreSQL and Oracle preview profiles.

An unaliased application table keeps its logical name as a visible alias when
the storage relation is schema-qualified. This preserves `table.column` filters,
projections, wildcard projections, joins and correlated outer references. An
explicit SQL alias stays unchanged. UPDATE and DELETE predicates use the same
logical binding; COPY retains its table-target binding.
Named index, sequence and view creation and table/index/sequence/view removal
also bind unqualified targets to that application schema. Explicit namespaces
retain their selection. PostgreSQL driver `DEALLOCATE` commands preserve native
prepared-statement identifiers, including quoted mixed-case names; these names
are independent of Oracle application-name folding.
When an ordinary column and a row alias share a name, type inference prefers
the scalar column, matching row evaluation and preserving driver scalar types.
PostgreSQL protocol Describe also resolves explicit, fully typed FROM
projections from metadata. Preparing those queries does not run their joins,
filters or projections; a row-dependent expression error is reported when the
query executes. Wildcard and unresolved projection paths retain their existing
fallback and are not qualified by this change.

Oracle `FOR UPDATE OF column` resolves the owning base-table alias and lowers
to the native table-lock target. Qualified columns in inner joins lock their
owning table, rather than every joined table. Missing or ambiguous owners fail.
The native row-lock implementation now distinguishes the logical OF target from
the physical row-set prefix, including schema-qualified quoted tables. Native
locking, retry and error contracts still apply; Oracle blocking and isolation
conformance are not claimed. INSERT, UPDATE and COPY column names also retain
Oracle folding when a column is named with an otherwise syntactic word such as
VALUE.

For a READ COMMITTED locking SELECT, the first row lock waits for its owner
without an immediate transaction-age rejection. The wait remains bounded by the
native reservation budget. After an owner commits, the locking query refreshes
and rechecks the row before returning it. Transactions already holding row locks
retain native deadlock-avoidance behavior; repeatable-read snapshots retain their
existing conflict contract. Driver regression tests cover both PostgreSQL and
Oracle-preview connections. The
[application runtime evidence](evidence/idempiere-runtime-2026-11-01/README.md)
records a concurrent sequence-allocation check, not full transaction conformance.

## Native unique index policies

`CREATE UNIQUE INDEX ... NULLS NOT DISTINCT` compares NULL components as equal.
Without that explicit option, PostgreSQL's ordinary NULLS DISTINCT behavior is
preserved. Oracle composite uniqueness additionally permits duplicate all-NULL
keys; the migration tool excludes those rows with a partial-index predicate when
necessary.

Ordinary UNIQUE column/table constraints created in the preview now use the same
Oracle NULL rules. Single-column keys permit repeated NULLs. Composite keys
reject equal partially NULL keys and omit wholly NULL keys. The persisted database
profile selects this default; a mutable session setting cannot change it.
PostgreSQL databases retain ordinary NULLS DISTINCT behavior. Explicit table
`UNIQUE NULLS NOT DISTINCT (...)` and `UNIQUE NULLS DISTINCT (...)` clauses select
their named native policy. Inline column NULLS clauses remain outside the parser
contract.

Each new non-default constraint persists a separate schema wire tag so older SQL
readers reject its metadata. Existing constraints keep their recorded policy and
are never silently reinterpreted on reopen. Their owning database must be upgraded
with a compatible binary before explicitly replacing older constraints. Constraint
backing indexes are exposed through `pg_constraint.conindid`, `pg_index` and
`pg_indexes`. The standard `information_schema.table_constraints.nulls_distinct`
field is NULL for an all-nullable composite Oracle key: neither YES nor NO can
represent its all-NULL exception. Non-NULL anchors use NO. The migration importer
checks both that policy and the executable index state on resume and before data
import/verification. See the [constraint evidence](evidence/idempiere-unique-constraints-2026-11-01/README.md).

These are immediate, non-deferrable UNIQUE rules. Deferrable constraints and
foreign-key migration remain separate requirements.

Native `UPPER` and type-preserving two-argument `COALESCE` fields provide actual
index backfill and write enforcement. COALESCE supports compatible text/varchar,
integer, numeric and boolean scalar inputs with compatible literal fallbacks.
Numeric integer defaults use exact canonical keys. Fractional floating literals,
volatile fallbacks and value-changing input casts are rejected for unique indexes;
this is a bounded expression subset, not general expression indexing. Its case
conversion follows the engine's existing ASCII behavior, not Oracle NLS rules.
Metadata-only non-unique placeholders are neither valid nor ready; unsupported
expressions cannot create unique placeholders.

The on-disk index policy has a capability flag. Its extended uniqueness wire
encoding also makes older readers/replication peers reject it. Existing ordinary
indexes retain their boolean encoding. Enabling this feature requires compatible
binaries; the capability flag is retained after index removal. This is not a
qualified cluster upgrade or downgrade procedure. The
[development evidence](evidence/idempiere-nullable-indexes-2026-11-01/README.md)
records runtime checks against Oracle and an older development binary.

## Datetime truncation

Datetime `EXTRACT` retains its field grammar rather than folding the field as an
application column. Conditional aggregates using extracted years are covered by
native query tests and [Oracle comparisons](evidence/oracle-extract-2026-11-01/README.md).
This does not qualify every Oracle extraction overload or error condition.

Known date/timestamp operands support numeric day addition/subtraction and
number-plus-datetime in ordinary preview queries. Numeric timestamp arithmetic
discards fractional seconds; day offsets round to whole seconds with exact
decimal arithmetic. Literal offsets retain their token precision. Declared
parameter types select the overload; undeclared day parameters infer NUMERIC.
CTEs and derived queries retain the datetime result type. See the
[day-offset evidence](evidence/oracle-day-offsets-2026-11-01/README.md).

Preview integer/NUMERIC division now produces a decimal quotient, including an
offset expression such as `1/86400`. Its quotient precision follows twenty
base-100 mantissa digits. Declared parameters keep their wire types; undeclared
quotient operands infer NUMERIC. See the [division evidence](evidence/oracle-number-division-2026-11-01/README.md).

This does not complete NUMBER storage, literal conversion or other arithmetic
operators. Date-minus-date, time-zone overloads, NLS conversion, binary-floating
overloads and arithmetic inside stored programs need separate implementation or
qualification. Default PostgreSQL operators and the bounded HR profile retain
their existing behavior.

The preview resolves `TRUNC` on known date/timestamp expressions to an Oracle
datetime helper returning native `timestamp` (the mapping for Oracle DATE).
Resolution uses metadata, including ordinary CTE projections, without executing
queries. Explicit PostgreSQL Parse parameter OIDs for date and timestamp also
select this overload. Numeric `trunc` and the default PostgreSQL profile retain
their existing behavior. Unspecified or text parameter types are not guessed to
be datetime values.

Supported format groups are day (`DD`, `DDD`, `J`, and the omitted default),
month (`MM`, `MON`, `MONTH`, `RM`), year (`YYYY`, `YYY`, `YY`, `Y`, `YEAR`,
`SYEAR`, `SYYYY`), quarter (`Q`), ISO week (`IW`), hour (`HH`, `HH12`, `HH24`),
minute (`MI`) and century (`CC`, `SCC`). Other formats fail explicitly. This
does not establish NLS-dependent week rules, timezone overloads, general Oracle
implicit conversions, or datetime truncation of untyped PL/SQL variables.
The [reference evidence](evidence/oracle-datetime-2026-11-01/README.md) records
14 query-value comparisons against an installed Oracle reference.

Oracle LOB APIs, full LAX JSON rules, character padding/encoding equivalence,
Oracle catalogs, PL/SQL packages, autonomous transactions, Oracle transaction
semantics and general application compatibility are not established by these
mappings. Oracle DATE uses native timestamp(0) transport and storage, with
source metadata selecting whole-second truncation; unconstrained NUMBER uses native
numeric. Migration acceptance must test the actual application values and
operations, including NULL versus empty LOBs, byte lengths and timezone values.

## Stored-function declarations

The preview adapts ordinary standalone Oracle function declarations to the native
PL/pgSQL interpreter: `RETURN` result types, omitted empty parameter lists,
parameter modes after names, local declarations before `BEGIN`, named outer
`END` statements and a final SQL*Plus slash delimiter. Parameter defaults can
contain nested casts. The existing procedure path also normalizes parameter
modes and local declaration sections. PostgreSQL procedural expressions resolve
quoted parameter names consistently in builtin arguments and direct returns.

New preview routine definitions persist the language marker
`bicdb_oracle_preview_v13`. It selects the tested preview routine compiler and
requires the database's durable Oracle preview profile. PostgreSQL and HR
databases cannot enable it with a connection setting. Native `LANGUAGE plpgsql`
definitions created through the native backend retain native behavior, including
previously translated routines; recreate an Oracle-authored definition to select
the new compiler. The compiler versions have separate `pg_language` identities,
present only in a preview database. Versions 1 through 12 remain readable.
Version 5 (OID 999404) fences CASE selector dispatch. Version 6 (OID 999405)
adds the tested Oracle statement-rollback and strict SELECT INTO contracts;
earlier definitions retain their previous block-rollback behavior. Recreate an
Oracle source definition to select these new contracts. The database storage
format is unchanged; these are stored-routine capability markers.

Version 7 (OID 999406) adds typed routine concatenation and one-argument
`TO_CHAR` for resolved character, NUMBER and logical DATE expressions. NULL is
an empty operand for Oracle concatenation; an empty final result is NULL.
Character padding is retained. Numeric conversion uses exact decimals and the
recorded dot-decimal NLS default. Implicit numeric fields have the independently
measured 40-character SQL and 100-character procedural widths, including
scientific formatting when required. Default DATE text uses English
`DD-MON-RR` with the Gregorian calendar. The preview does not implement mutable
NLS settings. Binary floating, national-character, LOB, BC date and unresolved
implicit operand types remain outside this contract and need explicit, supported
conversion. Legacy temporal columns require source-driven provenance backfill.

The tested character concatenation limits are 4,000 bytes for SQL expressions
and 32,767 bytes for procedural expressions. A character-valued Oracle function
called from SQL also enforces the SQL result limit; an internal procedural
caller can consume the longer value. SQL inside a routine retains SQL limits,
including after handled errors. UTF-8 byte boundaries are tested against an
AL32UTF8 reference. Versions 1–6 and native `LANGUAGE plpgsql` retain their earlier
concatenation and result contracts. Existing definitions must be explicitly
recreated to select version 7. Broader standalone SQL implicit conversions and
all Oracle length/type combinations are not qualified by the routine compiler.
The [concatenation evidence](evidence/oracle-routine-concatenation-2026-11-02/README.md)
records reference limits, error cases, source routines and PostgreSQL controls.

Version 8 (OID 999407) adds typed bound-cursor parameters for positional,
named and mixed calls, explicit OPEN/FETCH/CLOSE and cursor FOR loops. Oracle
formal defaults are evaluated at OPEN, only when omitted. Actual expressions
are evaluated once before query-local bindings replace enclosing values. Formal
values and types are restored before the loop body and after query errors;
nested declarations retain their own cursor state. Logical DATE formals discard
fractional seconds. Oracle table columns take precedence over same-named cursor
parameters; native PostgreSQL cursor formals report ambiguous column references.
Native cursor formal defaults remain rejected. Versions 1–7 reject the new
Oracle parameterized declarations. Refcursors, scrolling, complete cursor
attributes, portal/streaming behavior and full compile-time diagnostics remain
outside this bounded contract.

Version 8 also rounds resolved NUMBER arithmetic to the measured twenty-base-100
mantissa digits, instead of leaving unlimited native decimal intermediates. It
keeps DATE day-fraction arithmetic consistent when a result is multiplied back
into seconds. SQL and procedural arithmetic carry separate execution contexts:
the tested SQL overflow raises 22003, while the procedural path can produce
NUMBER infinity. Infinity uses native PostgreSQL NUMERIC transport, including
`Infinity` and `-Infinity`, and default Oracle character conversion emits `~`
and `-~`. Oracle NUMBER infinity operations have independently measured behavior
that differs from IEEE arithmetic. Native PostgreSQL and versions 1–7 retain
their arithmetic contracts. General NUMBER input/column constraints, integer
literal/PLS_INTEGER overflow semantics, all conversions and other Oracle versions
are not established by these tests.
The [cursor and arithmetic qualification](evidence/oracle-parameterized-cursors-2026-11-02/README.md)
records the source comparisons, transport policy, older-reader fence and remaining
application failures.

Version 9 (OID 999408) adds type-directed DECODE in stored SQL. The preview
also resolves ordinary SQL DECODE after namespace and PostgreSQL parameter-type
binding. Resolved character, NUMBER, logical DATE and TIMESTAMP inputs use the
first search/result conversion rules, NULL equality, nonpadded character
comparison and lazy searches/results. The selector is evaluated once. Direct
procedural DECODE requires an embedded SQL statement. Versions 1–8 retain their
earlier compiler behavior; explicitly recreate source definitions to select
version 9. Mutable NLS, implicit character-to-TIMESTAMP, binary floating point,
national/LOB types, unmarked legacy temporal columns and broader conversion rules
remain unqualified. Native PostgreSQL binary decode is independent. The
[DECODE evidence](evidence/oracle-decode-2026-11-02/README.md) records values,
metadata, typed binds, native controls, cursor type-cache recovery and the
unchanged original business-date routine.

Version 10 (OID 999409) adds CHR under the preview's fixed AL32UTF8 character
set. It interprets the argument as packed UTF-8 bytes for one complete character,
including multibyte and supplementary characters. Numeric arguments truncate
their fractional part; negative, nonzero sub-unit and overflowing values report
22003. SQL and procedural reference errors have different Oracle wrapping
(ORA-01426 versus ORA-06502); both use numeric-overflow SQLSTATE 22003 over the
selected PostgreSQL transport. Full Oracle error identity is not established.

The compiler and ordinary SQL resolve default TO_CHAR on nested CHR and other
known character, NUMBER and logical DATE expressions. PostgreSQL Parse parameter
types participate in overload resolution. SQL results retain native text types,
and declared routine returns retain their native VARCHAR representation.
Prepared-call recovery and reopen are tested. Existing versions 1–9 keep their
earlier CHR interpretation; recreate unchanged Oracle source to select version
10. Native PostgreSQL chr independently uses Unicode scalar numbers and strict
NULL behavior. The [Oracle CHR reference](https://docs.oracle.com/en/database/oracle/oracle-database/26/sqlrf/CHR.html)
describes the character-set-dependent input representation.
Older stored defaults or views containing untranslated CHR also need explicit
source recreation; the temporal column backfill does not rewrite their SQL.

NUL cannot be represented as native PostgreSQL text and fails explicitly with
0A000. Invalid packed characters also fail explicitly; Oracle specifies their
results as indeterminate. NCHAR_CS and other database character sets remain
unqualified. This is not a general globalization compatibility claim.

COALESCE now short-circuits in scalar session queries, database-aware constant
projections, record/default/update evaluation and specialized catalog evaluation,
as it already did in bound row execution. An unused failing argument is not
executed; common-type validation still runs. This general correction applies to
both profiles and is independent of application names or routine versions.

Version 11 (OID 999410) adds eager, type-directed NVL for resolved character,
NUMBER, logical DATE and TIMESTAMP operands. Both operands and their required
conversions execute before selection. The first character operand selects a
character result; an empty character literal retains that type while its value
is NULL. The first operand's character length or NUMBER precision does not
constrain the replacement. Incompatible numeric/datetime operands fail with
42804. COALESCE retains its independent lazy evaluation contract. These
conversion checks cover runtime typed operands. Oracle's PL/SQL constant
propagation can elide an otherwise unused conversion and remains a separate
unimplemented contract, recorded with the version-12 observations.

NVL preserves character padding and carries timestamp precision through base
columns, CTEs, derived queries, cursor records, local variables and anchored
returns. SQL timestamp literals, binds and stored function results use nine
fractional display digits; procedural variables use their declared precision
(six by default). An anchored TIMESTAMP return rounds to its source column's
precision before SQL applies result formatting. DATE replacement discards
timestamp fractional seconds. Values with nonzero fractional digits beyond
microseconds fail explicitly instead of silently losing precision.

These conversions use the preview's fixed numeric, date and timestamp NLS
defaults. Binary floating point, national/LOB operands, intervals, other NLS
settings and full Oracle optimizer/type-resolution diagnostics are unqualified.
Versions 1–10 retain their stored NVL translations; recreate original Oracle
source to select the version-11 compiler. An older reader rejects a version-11
routine with 0A000. This marker adds no database storage-format transition.

Version 12 (OID 999411) adds stored Oracle procedure compilation and namespace
binding. The header parser handles CREATE OR REPLACE, quoted names, parameterless
Oracle declarations and positional/named arguments. Procedure metadata retains
its procedure kind. Static table references and nested CALLs bind to the
procedure's declared schema. Earlier function compiler versions remain readable;
new preview procedures require version 12. An older reader rejects their calls
with 0A000, without executing the body.

Version 13 (OID 999412) adds scoped parsing of Oracle `(+)` predicates in static
queries and cursor declarations, and column-owner binding for multi-column
`FOR UPDATE OF` lists inside stored routines. Conjunctive predicates are lowered
to explicit LEFT JOINs: marked optional-side filters stay in ON, unmarked
filters stay in WHERE, dependency order is preserved, and plain `*` retains the
original FROM-list column order. Mixed ANSI/legacy join blocks, cyclic
dependencies, ambiguous column ownership, markers outside supported WHERE
predicates and marked OR/IN expressions fail explicitly. This is a bounded
grammar implementation, not full Oracle join syntax or diagnostics.

Oracle preview DELETE statements may omit FROM. Shared procedural parsing now
accepts mixed-case FOR keywords and whitespace or comments between END and LOOP.
Shared SQL parsing accepts native PostgreSQL FOR UPDATE/SHARE target lists without
changing their relation-target meaning; Oracle OF items select columns whose
owning tables are resolved using the catalog. NOWAIT/SKIP LOCKED modifiers are
preserved. Existing row-locking restrictions, including the primary-key
requirement, still apply. Recreate original Oracle definitions to select the new
compiler; native PostgreSQL routines do not inherit the Oracle grammar scope.
An older reader rejects version-13 calls with 0A000. No storage-format transition
is introduced by this compiler marker.

Shared CALL handling now excludes OUT placeholder values from input frames,
retains IN OUT values, and copies successful nested-call outputs back to writable
caller variables. Top-level PostgreSQL CALL returns output rows with declared
transport types, including NULL outputs; logical Oracle DATE uses TIMESTAMP OID
1114, while native PostgreSQL DATE uses OID 1082. Qualified calls reject the wrong
schema. Existing raw procedure parameter-mode spellings remain accepted. These
shared CALL corrections apply to the native interpreter as well as the preview.
Native PostgreSQL empty strings and calendar dates retain their own behavior. Native
BicDB procedures also retain the existing compact CALL extension, which omits
pure OUT slots from positional calls. This extension differs from PostgreSQL's
arity rules and is recorded separately from PostgreSQL-equivalent cases. New
Oracle-authored procedures require all declared output argument slots.

This does not qualify packages, autonomous transactions, transaction control,
dynamic SQL, all overload/type-resolution rules or the remaining application
procedure bodies. PL/SQL constant propagation around NVL, PLS_INTEGER declarations
and formatless TO_NUMBER still have independently observed gaps; the bounded
NVL cases above do not establish those contracts.

Version 2 binds static relation references in functions to the namespace in the
stored function declaration. Unqualified declarations created through the
preview session front end use its selected application schema. Quoted namespace
spelling is retained in routine metadata and qualified DROP checks. The common
relation visitor preserves CTE names, explicit qualifications and visible table
aliases. Native table privileges still apply; Oracle AUTHID rights are not
established. Dynamic SQL namespace binding and version-2/3 procedures are explicitly
unsupported. Routine names still use global normalized keys: this does not
provide schema-isolated overloads or full qualified routine-call resolution.

Version 3 retains source DATE declarations separately from their physical
PostgreSQL timestamp representation. DATE parameters, assignments, casts and
returns discard fractional seconds; a declared TIMESTAMP(0) still rounds.
DATE plus/minus NUMBER returns DATE, DATE minus DATE returns exact NUMBER day
fractions, and explicit TIMESTAMP differences return intervals. Numeric
expressions use the preview's exact NUMBER division. Declared numeric fields
from cursor query metadata participate in arithmetic. Metadata inference does
not execute queries; schema changes invalidate the typed routine cache.

Procedural `TRUNC` resolves declared DATE/timestamp parameters and locals,
including initializers, assignments, conditions and returns. Numeric TRUNC
remains numeric. Physical timestamp columns and temporal `%TYPE` anchors do not
establish their original Oracle DATE/TIMESTAMP identity; arithmetic requiring
that identity fails explicitly. Timezone arithmetic, timestamps beyond six
fractional digits, general SQL overload resolution and full record typing are
not qualified. The preview implements Gregorian ADD_MONTHS for scalar and
version-3 routine expressions: month-end carry, exact truncated month counts,
whole-second DATE results and NULLs. Native PostgreSQL interval addition and
qualified user functions retain their existing behavior. Alternate NLS calendars,
timezone conversion, BC boundary conformance and Oracle-specific error codes
remain unqualified; other calendar functions remain separate work.

The [routine datetime evidence](evidence/oracle-routine-datetime-2026-11-01/README.md)
records version-1 values and its original application namespace failure. The
[static namespace evidence](evidence/oracle-routine-namespaces-2026-11-01/README.md)
records version-2 comparisons and the original arithmetic gap. The
[typed arithmetic evidence](evidence/oracle-routine-arithmetic-2026-11-01/README.md)
records version-3 reference comparisons, PostgreSQL isolation and limitations.

Version 4 distinguishes procedural date-format validation from embedded SQL.
SQL TRUNC(date, NULL) returns NULL. A procedural expression raises an error for
a non-NULL datetime and NULL format (SQLSTATE 22023 over the PostgreSQL
transport); a NULL datetime still returns NULL. Numeric TRUNC retains NULL
propagation. Stored version-3 definitions retain their earlier NULL-format
behavior until recreated from source. Numeric NUMBER truncation in the new
compiler uses exact decimal coefficients. SQL truncates a fractional precision
toward zero; procedural calls round precision halfway away from zero to satisfy
the builtin integer parameter. The native two-argument numeric overload takes integer precision
and preserves its decimal display scale.

The preview supports W (weeks from the month's first day), WW (weeks from the
year's first day), ISO weeks/year starts, and D/DY/DAY with its AMERICA default
(Sunday). Gregorian/AMERICA reference settings are required for the generated
week suite. Alternate NLS territories and general NLS session configuration
remain unsupported. Stored SQL and top-level SQL share the one-row DUAL
lowering, with explicit aliases and CTE shadowing retained.
The [week and procedural-format evidence](evidence/oracle-week-truncation-2026-11-01/README.md)
records the reference assertions and remaining limits.

Table-column `%TYPE` anchors resolve in the routine definition's namespace.
An explicit `[schema.]table.column%TYPE` retains quoted identifier case and uses
the same physical relation encoding as ordinary SQL. Session schema selection
is applied before resolving anchors for an unqualified definition. A missing
owner table does not fall back to a same-named public table.

For the tested mapped NUMBER and VARCHAR2 CHAR types, local variables inherit
precision/scale and character length, while defaults and column NOT NULL do not
transfer. Argument modifiers remain unconstrained. Character return lengths are
unconstrained, but a constrained numeric return rounds and range-checks before
returning; its own exception handler can catch a conversion error. The compiler
encodes that numeric conversion as an explicit CAST in the stored body, including
exact literal operands. Default PostgreSQL declarations retain their native
signature-modifier behavior.
Procedural fallback evaluation also resolves unary operands from the live frame
and uses declared types for numeric, integer and interval negation. This retains
NULL propagation, exact numeric values and integer range checks in CASE
expressions without evaluating unselected branches.

Anchors are materialized when a source definition is created or replaced.
Automatic Oracle dependency invalidation and recompilation after column DDL
remain outstanding; recreate the source definition to refresh its mapped type.
Temporal anchors require durable source logical-type provenance rather
than guessing DATE from a physical timestamp. New temporal columns retain that
provenance; legacy columns require an explicit source declaration. Variable/record anchors, general
BYTE versus CHAR behavior, user-defined Oracle types and cross-schema privilege
qualification remain outstanding.
The [column-anchor evidence](evidence/oracle-column-anchors-2026-11-02/README.md)
records reference comparisons, original routine retries and remaining blockers.

## Durable temporal column declarations

In a durably provisioned preview database, new DATE and TIMESTAMP columns retain
their Oracle logical declaration separately from their native PostgreSQL type.
DATE assignments, including COPY, discard fractional seconds. TIMESTAMP(n)
assignments round to n digits; omitted precision means six. DATE and timestamp
columns use PostgreSQL timestamp OID 1114, and TIMESTAMP WITH TIME ZONE uses OID
1184. Native PostgreSQL databases retain calendar DATE and native rounding.

The read-only `bicdb_oracle_column_type(relation_text,column_text)` accessor
returns the source declaration or NULL for absent or unmarked columns. Pass
quoted, qualified relation text and the exact column name. Temporal `%TYPE`
anchors resolve marked columns, including quoted names. Query arithmetic traces
base columns through aliases, CTEs, derived tables and cursor records; unknown
lineage remains unsupported when DATE identity is required. This does not add
automatic routine dependency recompilation or qualify timezone region behavior.

Persisting these modifiers promotes the preview profile metadata to format 2
with feature `oracle_temporal_columns_v1`. Composite attributes use the same
reader fence. Older binaries reject that profile rather than reinterpret DATE
as a rounding timestamp. The promotion is conservative and may remain after a
transaction rolls back its DDL. Keep a pre-upgrade backup for binary rollback;
native backup/restore preserves the logical metadata.

For legacy imported columns, single-column `ALTER TABLE ... MODIFY (column
DATE)` or `... MODIFY (column TIMESTAMP(n))` supplies the source declaration.
Physical timestamp precision alone never establishes DATE identity. The normal
row, default, constraint and index checks still apply. Reconciling an unmarked
column with identical physical storage can preserve dependent views; changing
an already declared logical type retains the ordinary dependency guard.

Procedural simple and searched CASE statements use the shared routine
interpreter. The scalar selector is evaluated once; conditions stop at the
first match, and only that branch's statements execute. NULL does not match
NULL in simple CASE. An omitted ELSE with no matching branch raises SQLSTATE
20000 (CASE_NOT_FOUND), independently of scalar SQL CASE's implicit NULL
result. Named CASE_NOT_FOUND handlers, nesting, query statements, RETURN,
CONTINUE and EXIT retain their ordinary routine behavior. Definition namespace
binding and declared-type arithmetic recurse through every arm. The adaptive
compiler uses the interpreter for these blocks.

The [generated CASE fixture](../examples/oracle/reference/routine_case.py) has
34 independently checked Oracle expectations. Native PostgreSQL regressions
retain integer division, which differs from Oracle NUMBER division in a CASE
condition. PostgreSQL comma-separated simple-case alternatives remain supported; their
Oracle grammar/behavior is not qualified. Labels, newer selector predicates and
full Oracle conversion semantics remain unqualified.
Native routine definitions currently compile on invocation; Oracle-compatible
DDL validation and invalidation remain separate outstanding work.

Nested BEGIN/END and DECLARE blocks share the routine interpreter. Local
declarations shadow values, assignment types and cursors, then restore the outer
bindings on normal completion, errors and loop/return exits. A declaration's
initialization error propagates to the enclosing block. An error raised inside
a selected handler propagates outward instead of selecting a second handler
from that same block. Native routines retain PostgreSQL block rollback and
local-variable state. New version-6 Oracle routines retain prior successful
statements when a later error is handled, while undoing a failed statement's
partial writes. Their SELECT INTO raises NO_DATA_FOUND or TOO_MANY_ROWS rather
than adopting PostgreSQL's non-strict zero/first-row behavior. These are bounded
contracts; bare rethrow, stacked diagnostics, user-defined exceptions,
autonomous work and general transaction/error continuation remain unqualified.
Native LANGUAGE plpgsql routines inside a preview database retain native policy.

Preview anonymous blocks carry their language explicitly after the DO body;
native DO blocks keep PostgreSQL behavior. The routine-resolution cache also
includes database instance identity for positive and negative entries, preventing
cross-database reuse when catalog generations happen to match.

ROWNUM supports conjunctive prefix comparisons with literal integer bounds in
plain query blocks, including comparisons written with the operands reversed.
It counts the accepted prefix, so ROWNUM=2 and ROWNUM>1 produce no rows. Ordered
prefix selection requires ordering in an inner query. Same-block ORDER BY,
grouping/aggregates, projection of ROWNUM, disjunctions, non-integer or dynamic
bounds and mixed native row limits remain explicitly unsupported. This is not
a general ROWNUM-to-LIMIT substitution. Native PostgreSQL columns named rownum
retain their normal meaning. The public [prefix fixture](../examples/oracle/reference/rownum-cases.json)
contains 15 independently checked Oracle expectations.

This is declaration support for the tested routine subset, not a complete
PL/SQL compiler. Native routine execution, namespace, overload, privilege and
error contracts still apply. Oracle AUTHID/rights semantics are not qualified.
Packages still fail explicitly. Version-15 standalone autonomous routines have
the bounded contract described below. Other routine bodies can require additional expression, cursor,
exception or application-schema adaptations. Accepted DDL alone is not proof
that every routine compiles and executes: migration acceptance must exercise
each required routine and its dependencies through the application driver.

## Independent routine transactions

New compiler-version-15 standalone functions and procedures accept a declaration
of `PRAGMA AUTONOMOUS_TRANSACTION;`. The persisted definition retains that
declaration and a versioned language identity. Older readers cannot silently
execute the new routine as an ordinary caller transaction.

The interpreter suspends its caller and opens a separate transaction. Child
COMMIT and ROLLBACK affect that child; earlier child commits survive later
errors, enclosing rollbacks and restart. Returning with uncommitted activity
raises ORA-06519 and rolls the remaining child work back. Successful zero-row
UPDATE/DELETE, savepoints and locking reads count as activity. An ordinary
read-only call and a caught failed INSERT need no commit. Formal argument
defaults execute before suspending the caller; declaration initializers execute
inside the callee. Diagnostic context is shared independently of data visibility.

The caller retains its writes and locks. A child waiting on a suspended
ancestor's row lock raises ORA-00060 without releasing the parent's lock.
READ COMMITTED callers refresh visibility after child commits. Oracle-preview
`SET TRANSACTION ISOLATION LEVEL SERIALIZABLE` pins the caller's snapshot;
child transactions still use their own current snapshots. Changing isolation
after row locking or mutation raises ORA-01453. This is a bounded Oracle
snapshot-isolation implementation, not PostgreSQL SERIALIZABLE support or a
qualification of concurrent Oracle serialization failures.

PostgreSQL transport Describe skips independent bodies and their omitted
defaults. Execution does not speculatively replay a statement after entering an
independent routine, including a failed commit attempt. Child execution uses
shared core APIs; operations requiring exclusive database access, including
child DDL and some sequence APIs, remain unsupported. Independent PostgreSQL
notification delivery is explicitly rejected. Packages, broad rights/session
state, distributed child commits and comprehensive failure injection remain
programme work. Native LANGUAGE plpgsql and the bounded HR profile retain their
separate contracts.

The [transaction evidence](evidence/oracle-autonomous-transactions-2026-11-03/README.md)
separates generated Oracle matches from definition acceptance and failing
original application calls.

## Bound anonymous submissions

The preview accepts PostgreSQL extended-protocol input parameters in raw Oracle
`BEGIN ... END` and `DECLARE ... BEGIN ... END` submissions. Parameter inference
uses declarations and supported SQL contexts without executing the block during
Parse or Describe. Bind preserves the namespace selected during Parse and lowers
the Oracle source with the decoded parameter values. Parameter-like text inside
strings, comments and native dollar-quoted routine bodies remains literal.
Native PostgreSQL `DO` bodies do not gain outer host parameters.

When a failed preview statement has restored its pending changes successfully,
the PostgreSQL transport permits the caller transaction to continue. Prior caller
writes remain pending. An explicit `COMMIT` inside a block remains durable if a
later operation fails; uncommitted writes after that boundary are rolled back.
The transport requires confirmation of cleanup rather than inferring transaction
health from a SQLSTATE. Default PostgreSQL failed-transaction behavior is unchanged.
Parse/Bind failures and errors without confirmed cleanup retain conservative
transaction-failure handling; this is not complete Oracle error continuation.

This server contract does not prevent a client library from splitting a block
before transmission. In particular, stock PostgreSQL JDBC preparation requires
separate integration to submit an Oracle block atomically with its input binds.
Callable OUT parameters, complete PL/SQL transaction conformance and Oracle LOB
locators are not qualified by anonymous input binding.
