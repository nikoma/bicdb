# 1.0.498-beta: materialize application SQL indexes during activation

Embedded application tables previously acquired their executable SQL primary-key
indexes during the first PGwire startup. A fresh six-module ERP store exceeded
its unchanged 30-second readiness deadline; a diagnostic recorded 1,668 fsync
calls before that failed startup ended. Partially initialized copied stores did
not reproduce the complete first-start workload.

Application activation now derives the missing primary-key and UNIQUE indexes
from each actual installed SQL schema. It validates existing definitions and
creates missing indexes through the compensating schema receipt. Index name
collisions, including a partial UNIQUE index shadowing a complete primary key,
fail rather than replacing constraint enforcement. Failed activation or upgrade
rolls the created indexes back together with its schema changes. The normal
PGwire legacy backfill and read-only standby behavior remain intact.

The Node public-SDK qualification checks indexes before any serve, no deferred
index writes on first serve, exact Decimal writes, role and tenant denials, real
failed populated upgrades, compensation, SIGKILL restart, and cold-copy recovery.
Run it against an explicitly pinned binary using
`crates/bicdb-app-runtime/tests/node-activation-indexes/qualify.mjs`.

The actual six-module ERP regression became ready in 2,577 ms on its fresh
store, with its index catalog unchanged by first serve. Its maximum-value
nonfinancial stock transfer, exact replay, SIGKILL restart and cold-copy
recovery passed 515 HTTP observations. Restart readiness was 2,848 ms and cold
recovery readiness was 2,848 ms. All readiness and request limits were unchanged.

These are component qualifications. They do not qualify the complete nine-module
ERP, financially governed stock parity, the Hub issuer workflow, or HA.
