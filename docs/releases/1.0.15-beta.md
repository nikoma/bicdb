# BicDB 1.0.15-beta

Release date: 2026-08-03

## Bounded authenticated streaming backups

- Replaces monolithic backup creation with the `BICBAK03` streaming format.
  Database files are hashed and copied through fixed buffers instead of being
  retained together in plaintext, compressed, and encrypted archive vectors.
- Encrypts the manifest separately and writes file payloads as ordered,
  independently authenticated 1 MiB XChaCha20-Poly1305 frames. Optional zstd
  compression is decided per frame and decompression is output-bounded.
- Binds each frame to the authenticated outer header, exact frame index, codec,
  and plaintext length. Truncation, corruption, insertion, and frame reordering
  fail closed.
- Bounds manifest/header memory to 64 MiB, file cardinality to one million,
  paths to 16 KiB, and accepted data frames to 4 MiB before allocation. Unsafe
  KDF parameters are rejected before Argon2 work begins.
- Applies the manifest memory bound while walking the source and reduces audit
  event recovery bounds in place instead of cloning the complete event log.
- Streams verification and final restored-manifest hashing. Restore first
  verifies the entire artifact, writes every file through a flushed temporary,
  and atomically publishes each completed file.
- Writes new backup artifacts through a guarded temporary, flushes them before
  rename, removes incomplete temporary output on failure, and preserves the
  previously published destination artifact.
- Detects source-file changes between manifest hashing and payload streaming
  instead of emitting an internally inconsistent archive.
- Gives the online checkpoint an OS-owned exclusive lock, rejects concurrent
  owners, and removes crash-left ownerless markers before subsequent writes.
- Rejects source and restore-path symbolic links, including a symlink supplied
  as a forced restore target, so backup and restore cannot escape their roots.
- Adds authenticated deletion entries to incremental archives, so applying an
  incremental removes files that disappeared after its base backup.
- Keeps encrypted JSON v1 and binary `BICBAK02` v2 verification and restore
  compatibility. Historical monolithic artifacts may still need proportional
  memory; all newly created artifacts use v3.

Timestamp PITR after file restore still materializes a logical historical
snapshot, and cluster-wide backup remains operator-coordinated. Those are
documented follow-up boundaries rather than silently weakened claims.
