# 1.0.532: user-type defaults, deferrable unique constraints

Part of the PostgreSQL SQL-parity work, checked against stock PostgreSQL 18.4
with `fixtures/postgres-compat/pgsql-parity/defaults-constraints.cases`
(40 cases, identical output).

## Fixed

- **Column defaults cast to a user-defined type** (`DEFAULT 'new'::status`,
  also schema-qualified, as `pg_dump` writes them) work for enum, domain and
  composite types in CREATE TABLE, ADD COLUMN and SET DEFAULT. They were
  refused with "column type ... is not registered".
- **`UNIQUE DEFERRABLE`** was accepted but checked immediately. Deferrable
  unique constraints are now checked at statement end (immediate mode) or at
  COMMIT / `SET CONSTRAINTS ... IMMEDIATE` (deferred mode); a duplicate left
  at commit fails with 23505 and rolls back. `PRIMARY KEY DEFERRABLE` and a
  deferrable unique constraint on a partitioned table return 0A000.
- **Dropping a primary-key column** drops the primary key with it, as in
  PostgreSQL (2BP01 when another table's foreign key references the key).
  Rows the open transaction has modified are not re-keyed under it (0A000).
- **`CREATE TABLE ... INHERITS`** was silently ignored, building a child
  without the parent's columns. It now returns 0A000 until inheritance is
  implemented.

## Changed

- `information_schema.columns.column_default` shows every column default, the
  same text as `pg_attrdef`, instead of only sequence defaults.
