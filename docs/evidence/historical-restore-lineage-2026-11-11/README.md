# Historical restore activation after metadata progress

This is a local metadata-consensus recovery defect and fix, separate from the Azure observations and the unresolved data-handoff image proof. It does not enable Strong reads, change restore certificate admission, or establish HA qualification.

The clean baseline regression `1586ba823ca8e978b65e4374ee9c9038b27363a1`, based on `81e65ccf`, uses three fsync-on `MetadataConsensusStore` instances. Actual granted votes elect the leader; ordinary Append replies commit its term barrier, a valid restore activation at topology generation 3/index 2, and a real `DistributionStore::update_range_load` successor at generation 4/index 3. Both leader and follower then refuse to reopen. The lagging store also rejects the elected leader's genuine compacted snapshot. All three errors say the restore activation does not match its metadata topology. The baseline command exits 101 because the preservation assertion fails; that original RED result is retained.

The cause is an invariant mismatch. `commit_entry` retains the committed restore activation when later ordinary topology entries contain no new activation. Reopen and snapshot validation nevertheless required the retained decision's original topology hash and generation to equal the latest topology forever.

The candidate separates two rules. **New restore decisions remain exactly bound to the topology at admission:** proposal and log-entry validation still require the complete original equality. **Retained committed lineage may describe an older topology:** it must retain valid IDs/digests, belong to the same cluster and never refer to a future generation. A decision at the current generation still requires the exact current hash. The metadata-acquisition DTO applies this same historical rule, with actual fresh-quorum positive and malformed-boundary negative checks.

Ordinary replication cannot erase committed lineage or rewrite a decision under the same activation ID. A different later decision must advance both the decision timestamp and, non-strictly, its topology generation. An identical complete snapshot decision is idempotent; new decision proposals still reject duplicates. Older snapshots remain ignored. Rejected higher-index snapshot DTOs leave committed state unchanged. A fresh authorized restore into a new root has no previous lineage to erase; its full certificate/admission workflow remains separate.

After compaction, the current topology cannot reconstruct an older activation's original topology hash. Historical lineage relies on the existing checksummed local consensus state and trusted authenticated snapshot-source boundary, plus strict original decision admission. It is not a fresh admission certificate, independently signed voter proof, or permission to restore arbitrary input. These tests exercise actual stores and vote/Append/read-index/snapshot APIs in process; they **do not exercise mTLS, VM faults or power loss**. Transport authentication was not changed.

No on-disk field or format version is added. Earlier binaries retain their old refusal of these historical states; a source fix is distinct from a compatible downgrade, published binary, deployment or production qualification. Exact source identities, commands, outcomes and resource samples are in `validation.json` and `checks/`.

Validation at candidate `8bf444aed155258dbfad202a965778dfee2fbb6f` passed all five `restore_activation` tests and all 19 `distribution_consensus::tests::` tests. These include the unchanged full restore-activation admission tests. The original `1586ba82` regression failed as expected; the first candidate compile at `598d5d3c` failed because an existing test's reopened follower binding needed `mut`. The single binding correction is retained in `8bf444ae`; no engine rule changed for that compile correction. All outcomes are retained separately, including compiler warnings.

Builds used one job, incremental compilation disabled and an active available-memory/pressure guard. The successful focused compile/test took about 61 seconds and retained at least 17.98 GiB available RAM; no guard interruption occurred. Metadata-consensus verification reused the resulting executable. These are local checks, not remote CI, release, deployment or qualification results.
