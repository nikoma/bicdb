# 1.0.506-beta: strong reads use the caller's whole budget; a lost data listener is restored

- **Strong reads listen past their slice.** The event client gave each read
  attempt part of the caller's budget and abandoned a member that was still
  executing. A dispatched read now stays in flight until the caller's
  deadline; the member is told the caller's remaining budget, never more
  (capped at five seconds), and at most one extra read is sent beside one
  still executing. Writes and scans already behave this way since
  1.0.505-beta.
- **A node can no longer be left without any listener during data open.** If
  the data listener start lost a momentary latch race after the control
  listener was drained, every retry failed at the metadata leader lookup
  before reaching the listener restart. Data open now restores a lost
  listener before that lookup, and the listener start repeats a busy refusal
  for up to 250 ms inside the open's own budget.
- **Tests.** The four-process operator CLI tests run one at a time in the
  workspace job, matching the policy for the in-process multi-node tests;
  this does not replace the listener fixes. The registered-image baseline
  repeats its non-waiting custody cut for up to two seconds and waits for its
  snapshot latch; no assertion changed.

Known limits: an operation that needs longer than the caller's whole budget
still fails with a timeout. The storage fault-injection test
`transaction_log_only_path_fails_closed_at_every_io_failure_site` failed
intermittently on two earlier heads of this change ("page_log.sync:60: the
fault was never reached") and passed on the final head and on main; its cause
is not known.
