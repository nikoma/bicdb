# 1.0.519-beta: first pieces of a cross-process range handoff

1.0.518-beta is reserved by a parallel candidate and is not used here.

Until now the only driver that moves a range onto a fifth member holds every
member's service in one process. This release adds the first pieces needed to
run the same stage logic from one coordinating process against members in
other processes. Nothing here is reachable by an operator yet.

## What is added

- **Backend seam.** The stage logic needs only four metadata operations from
  its hosts (`JoinedHandoffMetadataHosts`); each backend names its own hosts
  type. A backend can re-derive retained state from members before stage
  decisions (`resync`, `resync_before_abort`).
- **Remote backend skeleton** (`RemoteJoinedHandoffBackend`). It holds only
  member identities and the coordinator's transport. It reads an old voter's
  durable epoch, resolves members, sends the source Close round and re-derives
  "a cut was started" after a coordinator restart. Every other stage returns
  an explicit not-implemented error.
- **Step request.** One new member request lets a coordinator ask a member to
  perform its own local work. Its first operation makes the registered fifth
  member install its range image itself: it finds the donor, pulls and binds
  the image and retains its joint target. Repeated calls resume; a lost reply
  is safe to retry.
- **Remote decision proof.** The three metadata stages that change membership
  accept a sealed proof. Besides the in-process decision, a certificate built
  only from replies the transport authenticated (old majority, new majority,
  new leader) is accepted. A read-only request returns a member's durable
  decision so the certificate can be rebuilt.
- **Completion.** After serving, the driver records the activation of every
  new member and then the retired source's durable retirement record. The
  relocation ends `Completed`, a restarted driver recognises a finished
  handoff from metadata, and the range can be planned again.

## Validation

- Shared build host, lightly optimized test build, integrated branch: the new
  tests of each piece and the existing in-process driver tests pass in one
  serial run (23 passed, 0 failed). Each piece also passed the existing test
  groups around the code it touches, on its own branch.
- Full suite: the checks of the merged pull request.

- An independent read found no way to forge the decision proof or to commit a
  stage on unproven state. Three issues it raised are fixed here: decision
  reads and preparations are admitted only from handoff members or the
  permitted initiator and a read no longer uses a slot of a member's bounded
  request table; a target install step that has only reached discovery can
  be superseded; and becoming a data owner excludes an install step in
  flight.

## Limits

- A target install that has started cannot be discarded: a coordinator that
  returns with another attempt, or a superseded relocation, is refused until
  the target restarts.
- Source retirement can become unsatisfiable (a source that missed the
  decision publication, or whose incarnation changed after it wrote its
  record); the relocation then never completes. It fails closed.
- Rebuilding the decision proof needs the members' original in-memory
  attempt and the original phase; a restarted member refuses.
- A retired source's catalogue gains a field that older binaries reject.

- The coordinator must be the leader of the moved range to obtain a plan, and
  must also be the node that fenced the target. The intended first version
  requires the metadata leader and the range leader to be the same node.
- A remote coordinator cannot abort before the cut: the epoch read it needs is
  refused after the learner allocation. The abort is refused and commits
  nothing.
- A target restart during image install cannot resume, and a retained step
  has no release operation.
- The decision certificate cannot be rebuilt after the promotion commit.
- The retired source keeps its rows; retirement is a durable record, not
  physical cleanup. Moving the same range a second time is still refused by
  per-range state on the members that nothing clears yet.
- The new request and reply fields are not understood by older nodes.
