# BicDB 1.0.18-beta

Release date: 2026-08-03

## Durable distributed backup write fences

- Adds a checksummed range-write log v3 fence catalog. A fence binds one
  backup plan, range epoch, fully resolved log cut, installation time, and
  expiry, and survives process restart.
- Rejects every new range prepare above the fenced cut in `RangeWriteStore`,
  below SQL, pgwire, internal actions, and cluster RPC entry points. Idempotent
  retries at or below the cut remain safe.
- Refuses to fence an unresolved range tail, a stale epoch, a conflicting plan,
  or a duration beyond the bounded 24-hour plan window.
- Adds `RangeWriteCoordinator::fence_range_for_backup`: it drains the local
  admission reservation, performs bounded follower repair, fences the leader,
  and installs the identical cut on a current-voter quorum.
- Validates the complete plan/topology once into a private, non-deserializable
  `RangeBackupFenceSession`; per-range checks remain logarithmic rather than
  hashing the full range map for every fence.
- Adds authenticated cluster data protocol v12 install/release RPCs. Only the
  current range leader can fence a voting replica, and release requires the
  original plan plus canonical leader-inclusive quorum evidence.
- Releases remote selected voters before the leader. A remote failure leaves
  the leader closed for retry; failed partial installation rolls back every
  known installed fence it can reach.

Fence expiry is metadata, not an ambient-clock auto-unlock. The trusted backup
coordinator must explicitly release a completed/aborted/expired plan (or invoke
the explicit expired-fence cleanup with its trusted time). This deliberately
prefers write unavailability over silently advancing a still-captured cut.
