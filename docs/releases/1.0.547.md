# 1.0.547: two-phase commit

Checked against stock PostgreSQL 18.4 with the `prepared_xacts` regression
test and the two-phase commit cases in
`fixtures/postgres-compat/pgsql-parity/p.cases`.

## Added

- **Two-phase commit**: `PREPARE TRANSACTION 'gid'`, `COMMIT PREPARED`,
  `ROLLBACK PREPARED` and the `pg_prepared_xacts` view. A prepared transaction
  keeps its writes invisible and holds its row locks, unique keys and foreign-key
  reservations until it is resolved from any session. The prepare record is
  committed durably before PREPARE returns. Restart, crash recovery, backup and
  restore, and HA promotion bring every prepared transaction back with its locks.
  COMMIT PREPARED commits the data and ends the prepared state in one commit.
  Serializable transactions keep their read/write dependencies while prepared.
- **`max_prepared_transactions`**: defaults to 0 (disabled), as in PostgreSQL.
  Set it at server start with `--max-prepared-transactions N`, the
  `engine.max_prepared_transactions` configuration key or
  `BICDB_MAX_PREPARED_TRANSACTIONS`. `SET` refuses it with 55P02.
- PostgreSQL's errors: duplicate gid (42710), unknown gid (42704), gid of 200
  bytes or more (22023), COMMIT/ROLLBACK PREPARED inside a transaction block
  (25001), another role's transaction (42501), and the 0A000 refusals for
  NOTIFY/LISTEN, cursors WITH HOLD and mixed advisory lock levels.

## Not supported

- Transactions that ran DDL, hold transaction-level advisory locks or write a
  table with an exclusion constraint are refused with 0A000. So are distributed
  commit admission and PREPARE on a standby (25006). See
  `docs/postgresql-two-phase-commit.md`.
