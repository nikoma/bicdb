# BicDB 1.0.3-beta

## Bounded embedded-application performance

- Adds one shared pooled Wasmtime engine and epoch watchdog per application
  runtime, a configurable global instance-slot ceiling, and a bounded
  content-addressed compiled-module LRU. Validate followed by stage no longer
  compiles identical bytes twice.
- Disables Wasmtime's CPU-count-sized global parallel compiler pool. Module
  compilation occurs only on a cache miss, while steady-state hosting stays at
  a predictable thread ceiling.
- Prepares immutable Carrier execution plans at package load so a zero-hop
  request reuses the activated manifest and exact binding maps without cloning
  or revalidating the full package graph.
- Keeps binary request/response and signed-blob payloads on raw byte paths and
  applies byte limits without JSON-array expansion.
- Adds `bicdb app ... performance`, includes its bounded cache/pool counters in
  exported diagnostics, and adds a release-mode p50/p95, RSS, file-descriptor,
  thread, cache, and pool regression gate. The reference full-router baseline
  is p50 10 µs and p95 12 µs for 4,000 in-process requests.

## Canonical application ABI artifacts

- Makes `bicdb-extension` the explicit sole source of truth for application
  ABI v2 and publishes its versioned WIT/core-Wasm transport mapping under
  `abi/application-v2`.
- Adds canonical host-call request/response fixtures and a normative v2
  compatibility corpus covering defaults, future versions, unknown authority,
  unknown operations, and invalid response unions.
- Runs that corpus directly against the public Rust ABI without host features,
  and documents patch/minor/major compatibility and deprecation rules for
  compiler consumers.

## Atomic multi-application activation

- Adds `bicdb app ... activate-batch APP...` for exact-lock plugin graphs that
  cannot be upgraded safely one package at a time.
- Validates staged candidates and unchanged active dependents against the
  complete prospective catalog, prepares all schemas and supervisors, and
  publishes one durable catalog generation only after every readiness gate is
  green.
- Batch failure compensates schema work and preserves the previous coherent
  active graph; no mixed old/new dependency generation becomes routable.

## Compiler-signed Carrier tests

- Adds an optional, versioned `carrier_program.tests` contract containing the
  exact callable, input schema, deterministic seed, bounded case count,
  timeout, evidence requirement, and optional least-authority test identity.
- Adds `bicdb app ... test APPLICATION TEST`. Tests run only through this
  operator entry point; application routes and guest modules cannot acquire
  the private test capability.
- Authored `http.request` and `http.request_as` calls traverse the ordinary
  signed router, request coercion, roles/scopes, and response contract without
  granting network egress. Authored failure codes and messages retain their
  normal HTTP semantics.
- `--case-index` executes one compiler-signed deterministic property case.
  Carrier uses it with a fresh ephemeral BicDB database per case so mutation
  isolation matches generated Rust tests.
- Package validation binds every test to an existing callable and requires
  exact Tests and Observability feature authority plus the Observability host
  capability. Invalid bounds, impure identity expressions, missing callables,
  and forged authority fail before activation.
- Verified JWT `email` and `name` claims are materialized as trusted actor
  policy attributes, matching Carrier's `auth.current_user()` contract. A
  conflicting duplicate in the explicit `policy` claim fails authentication.
- Authored Carrier failures use the same deterministic message key, empty
  parameter map, and non-empty request identifier as generated Rust error
  responses, in addition to preserving the signed code and message.

BicDB 1.0.3-beta fixes a sync retry loop involving SQL `DATE` values and a
transaction lock leak that could leave rows unwritable until server restart.
It also adds the host-owned durable security runtime used by Carrier's BicDB
deployment target and native Carrier observability export.

## Carrier durable security runtime

- A compiler-signed `carrier_program.security` contract binds the exact auth
  helpers, verifier scheme, access/refresh lifetimes, host secret names, and
  replay/key-version/evidence requirements used by an application.
- BicDB implements durable Argon2 registration/login, password policy and
  breach digests, TOTP, versioned magic links, atomic OAuth PKCE state,
  host-signed access/refresh tokens, and restart-safe refresh sessions.
- The host owns exact register, login, refresh, logout, session-list, and
  session-revocation routes. A package cannot remove, forge, weaken, or replace
  those routes with guest callables.
- HS256 verifier configuration accepts an explicit overlap set of key ids.
  Refresh tokens and encrypted fields identify their secret-provider version,
  so an operator can retain the previous key during a bounded rotation window.
- Replay consumption, logout, revocation, and security evidence commit through
  application-scoped native BicDB records. They remain effective after process
  restart and cannot cross application boundaries.
- Package validation rejects missing helper capabilities, plaintext/packaged
  key authority, absent version metadata, longer-token upgrades, removed active
  helpers, and incompatible rollback snapshots.

Carrier's focused cross-repository suite exercises all 15 auth helpers,
canonical signing and install, refresh replay denial, restart recovery,
v1-to-v2 key overlap, logout, and revocation across another restart.

## Carrier native observability

- A compiler-signed `carrier_program.observability` contract binds service and
  route sampling, exact log/trace/metric/audit helpers, literal metric and audit
  names, recursive redaction, event bounds, durable audit, and W3C propagation.
- BicDB owns request, trace, correlation, and immediate causation identifiers
  across HTTP, jobs, schedules, workflows, egress, and nested services.
  Parent-aware sampling is deterministic and unsampled trace events are
  suppressed without suppressing authorized logs or metrics.
- Explicit audit records commit transactionally into application-scoped BicDB
  state and remain queryable with `bicdb app ... observations` after restart.
- Operator integration configuration can combine an append-only JSONL spool
  with native OTLP/HTTP protobuf or OTLP/gRPC export. Endpoints and credential
  headers remain outside packages and guest memory; queues are bounded and
  exporter loss cannot alter application transaction semantics.
- Activation readiness rejects a missing or mismatched signed exporter.
  Cleartext requires explicit operator opt-in, credential files retain strict
  permissions, and recursive PHI/secret redaction occurs before either sink.

Carrier's focused live suite verifies all three OTLP signals against a real
collector boundary, per-route sampling, W3C response propagation, async job
ancestry, JSONL evidence, wire-level PHI/secret absence, and durable audit
equality across host restart.

## Carrier durable blob runtime

- A compiler-signed `carrier_program.blob` contract binds the exact reachable
  helper set, logical namespace, signed GET/PUT method set, byte limit, and
  mandatory virtual-file, durable-key, and evidence semantics.
- BicDB maps logical keys into opaque application-isolated provider namespaces.
  `blob.get` and `blob.put` use bounded host handles and invocation-local
  virtual files; a guest receives neither an ambient filesystem nor a physical
  provider path.
- The local provider supports atomic named overwrites, verified metadata and
  SHA-256, delete, record attachment, and HMAC-bound URLs at `/_bicdb/blob`.
  Signatures cover method, namespace, logical key, expiry, and download name.
- The modular `bicdb-blob-s3` production provider adds SigV4-compatible S3 and
  MinIO storage with operator-owned mode-`0600` credentials, explicit endpoint,
  region, bucket and least-privilege key prefix, bounded retries and bodies,
  optional SSE-S3/SSE-KMS, immutable overwrite generations, and verified reads.
  Credentials, physical keys, provider URLs, and response bodies stay outside
  guest memory and guest-visible errors.
- `bicdb app --blob-config` selects either the durable local provider or the S3
  module. S3 availability is health-checked before validation, lifecycle, and
  serving; signed client transfers remain policy-checked BicDB proxy URLs.
- Signed HTTP PUT enforces the active namespace's size, content-type, and scan
  policy. GET adds `nosniff`, hash ETag, and a validated optional attachment
  filename. Responses expose Carrier logical metadata rather than provider
  namespace or blob ids.
- Helper and signed-transfer operations emit host audit/evidence. Persistent
  bytes and still-valid URLs survive restart; active blob contracts cannot be
  removed or weakened during upgrade or rollback.
- Package and runtime validation reject forged helper/method/capability sets,
  traversal, ambient paths, expired or tampered URLs, request-method changes,
  duplicate or unknown query parameters, and oversized transfers.

Carrier's focused cross-repository suite builds, verifies, installs, and serves
the signed package; performs signed upload, virtual get/put copy, metadata/hash,
and signed download; exercises denial paths; and repeats persisted operations
after host restart.

## Carrier modular delivery providers

- ABI v2 service imports and exports can bilaterally sign
  `delegated_authority`. Legacy packages continue to execute with
  caller/callee authority intersection. A delegated service enters only the
  pinned, request-validated method under the callee's signed implementation
  authority; a one-sided value is rejected. Packages opting in must declare
  the new `delegated_service_authority` required feature.
- Carrier's generated provider packages use that boundary to keep SMTP or
  operator-bound HTTP authority inside narrow email, SMS, and payment
  services. Payment methods carry mandatory idempotency keys.
- `carrier_program.email` binds the exact `email.send` helper, operator
  provider, recipient/address/subject/body bounds, and mandatory evidence.
  Package validation rejects request-selected SMTP endpoints and missing
  egress/observability authority.
- The modular native `bicdb-provider-email` owns credential-free SMTP origins,
  mode-`0600` username/password files, TLS/cleartext policy, sender and optional
  recipient-domain allowlists, bounded pools, deadlines, MIME construction,
  and delivery receipts. Credentials and raw messages never enter guest WASM.
- Email evidence capacity is reserved before delivery and records only the
  provider, recipient count, and a domain-separated recipient-set digest.
  Missing providers, unauthorized recipients, invalid receipts, oversized
  messages, and exhausted evidence quotas fail closed before or around the
  provider effect as appropriate.

Carrier's focused four-package suite validates and installs an email, SMS,
payment, and gateway package; exercises SMTP and authenticated HTTP providers,
payment replay, missing providers, credential permissions and redaction,
recipient denial, and provider plus BicDB restart recovery.

## Carrier governed integration providers

- Dynamic Carrier HTTP/webhook endpoints and credential headers can bind to an
  exact operator-owned provider through `bicdb app --integration-config`.
  Packages retain only the provider name, required header names, schemes,
  relative paths, and bounded request authority; endpoints and values never
  enter application WASM or package artifacts.
- The host enforces application/provider matching, origin and base-path
  confinement, redirect and private-network policy, byte/deadline/admission
  bounds, response-header filtering, and startup health checks.
- The modular trusted `bicdb-provider-redis` implements compiler-signed
  `redis.publish` and `redis.incr` contracts with operator-owned credentials,
  bounded pools/timeouts, application-scoped channels, tenant-scoped keys, and
  pre-reserved evidence capacity. Non-idempotent operations are not retried.
- Missing or mismatched providers, path escapes, malformed contracts, bad
  credentials, permissive credential files, and unavailable dependencies fail
  closed with redacted errors. Focused acceptance covers persistence across
  Redis and BicDB restarts.

## Date round-trip compatibility

- SQL `DATE` values continue to be returned canonically as `YYYY-MM-DD`.
- BicDB now accepts the lossless UTC-midnight RFC 3339 representation emitted
  when JSON/JavaScript drivers serialize a date, for example
  `2026-08-01T00:00:00.000Z`, and stores it as `2026-08-01`.
- UTC-midnight values with `Z`, `+00:00`, or `-00:00` are accepted, including a
  numeric fractional-second component.
- Non-midnight timestamps and non-zero timezone offsets remain rejected rather
  than silently discarding or shifting time information.
- The compatibility applies to SQL literals, pgwire text parameters, typed
  storage, indexes, arrays, and WASM/browser SQL execution through the shared
  date codec.

Applications should still prefer `YYYY-MM-DD` for date-only values. The wider
input rule makes a server-to-client-to-server round trip safe when a driver
materializes a date as a JavaScript `Date`.

## Transaction cleanup

- Transactions now track every row lock they acquire, independently of their
  buffered write list.
- Commit, rollback, failed commit, connection/session drop, and abandoned
  transaction cleanup release pre-validation locks as well as completed-write
  locks.
- Savepoints capture both the write count and lock count. `ROLLBACK TO
  SAVEPOINT` releases only locks acquired after the savepoint and preserves
  earlier explicit row locks.
- Cleanup remains proportional to the number of locks owned by the transaction;
  it does not scan or serialize the global lock map.
- Lock waiters are notified when abandoned transaction locks are released.

This closes the failure mode where an `UPDATE` acquired its READ COMMITTED row
lock, then failed date/type/constraint validation before appending a buffered
write. Older releases derived cleanup keys only from buffered writes, leaving
that row owned by a transaction that no longer existed. A process restart
cleared the in-memory lock map; 1.0.3-beta clears it immediately on every
transaction termination path.

## Upgrade note

Upgrading restarts the BicDB process and therefore clears any locks already
poisoned by an older build. No storage migration or data rewrite is required.
