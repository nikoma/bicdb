# 1.0.521-beta: a range move across five separate processes

1.0.520-beta is reserved by a parallel candidate and is not used here.

1.0.519-beta added the first pieces of a cross-process range handoff. This
release completes the route: one operator command moves a replicated range
onto a fifth node while every member runs in its own process. It is an early
operator feature with real limits, listed below. Read them before using it.

## What is added

- **Operator commands.** `move-range` starts a move and `transfer-metadata-leadership`
  makes the metadata leader coincide with the range leader, which a move
  requires. The host status reports the move's stage, what it is waiting for
  and, when blocked, the member responsible.
- **Remote backend, complete.** The coordinator drives every stage over
  authenticated requests: readiness check of all members, source cut, image
  install on the target, decision round, the three membership commits,
  bridge preparation, publication and opening, custody retirement, release,
  writer policy, target serving, activation record and source retirement.
  One call walks a move to `Completed`; a restarted coordinator resumes from
  committed metadata.
- **Member steps.** Each member performs its own local work when asked,
  under its own freshly acquired role and its own reading of metadata.
  Requests carry identities only; no role, quorum or certificate is accepted
  from a request.
- **Certified scope in the committed record** (record version 2), so the
  promotion and final membership commits no longer need the decision proof
  to be re-collected after a restart.
- **Five-process acceptance test** in the CLI test suite: five hosts, a
  client appending and reading the moved range, the move to completion, and
  a check that every acknowledged append is readable afterwards.

- **Initial members can restart.** `serve-reopen` reopens an initial
  member's own root after a crash or stop. The member rejoins metadata as a
  follower, gets a new writer policy, opens data again and takes back the
  ranges it leads through the ordinary leader recovery, which needs a current
  quorum of the range's voters. A write the old process left committed in its
  own log but not yet applied is finished by the hot recovery. Nothing the old
  process held in memory is reused. A CLI test with four processes kills
  followers, a range leader, the metadata leader and then all four members,
  and checks that every acknowledged write can still be read.

## Review fixes included

- A decision is certified only when every new member and the retiring source
  hold it durably. A majority-only round could have stranded the range.
- All members are asked for readiness before the learner allocation is
  committed, and an abort before the cut works for a remote coordinator.
- An abort no longer reports "nothing committed" while a proposal of this
  host is undecided.
- A leadership transfer is refused while this host's move is unfinished.
- A reused or skipped operator sequence number is refused without ending the
  host; errors of a move step are reported.
- Members bind a step to the certified scope before keeping anything, release
  finished entries, and report "released" only after confirmation.

- A range that had been through a hot recovery would have been left
  unloadable by its next move: the source cut advanced the log epoch past
  the kept recovery record and the catalogue loader refused the file. The
  loader now accepts exactly that case (an activated recovery superseded by
  a durable promise of the same session, log at the promise's activation
  epoch), and a cut is verified before it is written. An independent review
  found no way to turn this into wrong data or revived old authority.
- Member steps no longer answer "not complete" on a timing edge under client
  traffic; the coordinator repeats a busy member by time, not by count, and
  starts the next stage without waiting for a supervisor tick.

## Limits

- **The moved range is unavailable during the move.** Strong reads and writes
  on it are refused from the learner allocation until the target serves.
  Between five processes on the shared build host, the same test measured 17
  to 19 seconds before the coordinator sent the member steps of one phase
  together. With the final code, three serial runs: move 13.9 to 14.8 s,
  strong reads refused for 12.1 to 14.7 s, writes for 11.8 to 13.8 s. No
  acknowledged write was lost. The allocation advances the range epoch, so
  the old voters cannot keep serving up to the cut without a protocol
  change.
- What the remaining time is made of (five processes, three new members):
  image install on the target 2.5 to 3.3 s, the decision 2.0 to 2.5 s, the
  three membership commits about 0.5 s, the activation about 7.2 s
  (preparation 0.25 s, publication 1.3 s, Open 1.5 s, custody retirement
  0.7 s, release 1.5 s, writer policy 1.8 s, target serve 0.2 s). A member's
  step reads every other member twice, and a member that is busy with its
  own step refuses such a read as busy and is asked again, so the
  coordinator asks at most two members at once for a
  publication, Open, release or writer policy and three for a preparation
  or custody retirement; more than that was measured slower, not faster.
  The metadata leader admits four metadata reads at a time.
- **Writes at the start of a move.** The coordinator holds new writes on the
  range for a moment, lets one in flight finish and then commits the
  allocation. The hold is kept until the coordinator has published the
  changed range, also when the outcome of the commit is unknown, for at most
  ten seconds; only a commit that can no longer happen ends it at once. If
  the ten seconds end first, the hold is released and the move status says
  so in `notes`; a write caught by that makes the coordinator refuse the
  cut, and the move must be aborted and started again. The hold exists only
  when the coordinator is an initial data owner; without it the status
  carries a note that the allocation was proposed without a write hold.
- A voter that holds an unfinished recovery of the range blocks the move
  before anything is committed. The refusal names the voter, the recovery
  record, its phase, who fenced it, the epoch it was fenced for and the
  epoch of the voter's range log. A record of an older epoch than the log is
  not skipped: a recovery may legitimately be fenced below the log's epoch
  while a handoff promise holds the log at its activation epoch.
- A source cut that fails on one member after another member kept its
  promise can only be resumed, not aborted. The known causes are refused
  before the cut.
- Nothing after the source cut can be aborted, and a member crash after the
  cut is not survivable for that range (no data is lost; the range stays
  unavailable).
- **Restart of an initial member (`serve-reopen`)** works only in the steady
  state: it is refused while any move is unfinished in committed metadata.
  There is no range leader failover: a range whose leader is down refuses
  writes until that member is back.
- A range leader killed while a write was in flight recovers its range only
  if its own log already certifies that write committed. If the write was
  only prepared on the leader, the range keeps refusing writes and reads
  after the restart (no acknowledged write is lost, and the status names the
  range and the reason). Recovering that case needs the native abort to be
  driven by the host, which does not exist yet.
- A member that is down during the decision round stalls the move.
- The coordinator must be both the metadata leader and the leader (and
  retiring source) of the moved range.
- **One move per cluster, and no further node after it.** After a
  completed move:
  - **Do not join another node.** A member publishes a node that joined
    into its writer policy by its own registry refresh, and that refresh
    accepts additions only while every range still has the configuration
    the policy was enrolled with. After a completed move it is refused on
    every member (the retired source and the members outside the moved
    range: the range configuration differs from the enrolled one; the
    surviving members of the moved range: the refresh proves the enrolled
    policy on a range that now has the handoff's serving configuration).
    Once the new node is a metadata voter, every member, the fifth node
    included, refuses Strong reads and appends on every range with
    "current voter registry changed". Measured between six processes; no
    recovery was tested.
  - A move onto such a node is refused by name before anything is
    committed: each voter now reports whether its writer policy covers the
    committed membership, and the coordinator asks before the learner
    allocation. Before this check the move got as far as the image, the
    donor's capture was refused and could not be started again.
  - The target must be an empty node that holds no range, so a second range
    cannot be moved onto the fifth node.
  - A node that joined through a move cannot coordinate a move or act as an
    old member of one, and it leads the range it received, so the same range
    cannot be moved a second time.
- The capacity of what a member retains for handoffs (its closures as an old
  member, its exports as an image donor) counts unfinished handoffs only;
  the retained state of finished ones is kept and no longer counts.
- Retired source rows are not physically removed.
- The new requests and record version 2 are not compatible with older
  binaries; do not mix versions in one cluster.

## Validation

- Shared build host, lightly optimized test build, integrated branch, serial
  runs: move, backend, step, certificate, completion and hold tests 59
  passed, 0 failed; in-process driver policy tests 36 passed, 0 failed;
  remote member tests 139 passed, 0 failed; operator command suite 6 passed,
  0 failed.
- Five-process acceptance test, three serial runs of the final code: 1
  passed, 0 failed each; every acknowledged append read back.
- A test fixture counted a read that the client itself had cancelled as a
  malformed evidence record, which failed two full-walk tests intermittently.
  The fixture now classifies exactly that record; every other incomplete
  record and any gap still fails.
