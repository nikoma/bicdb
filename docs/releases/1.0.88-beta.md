# BicDB 1.0.88-beta

## Streaming `AVG` aggregate

- `AVG(col)` — with or without a `WHERE` — now folds over the bounded
  streaming scan instead of materializing the table, joining the existing
  streaming COUNT/SUM/MIN/MAX/BOOL_AND/BOOL_OR simple aggregates. On a
  2,000,000-row paged table this is the difference between reading a batch at
  a time and materializing every row.
- The accumulator is an incremental `AverageState` (numeric/float running sum
  plus count) factored out of `average_aggregate_values`. The materializing
  path and the streaming path now share that one implementation, so the two
  execution strategies cannot drift apart.
- Non-distinct `AVG` only: `AVG(DISTINCT col)` still needs a dedup set and
  takes the materializing path, as before. Money-typed and non-numeric
  arguments decline exactly as the batch path dictates.

## Verification

- `streaming_aggregates.rs` extends the streamed-vs-materializing oracle
  (a transaction forces the streaming path to decline, so both answers come
  from the same engine with only the strategy differing) to integer and float
  `AVG`, filtered and unfiltered, NULL-heavy input, the empty set, and `AVG`
  mixed with COUNT/MAX — across both embedded and server-paged storage. A
  closed-form spot check pins `AVG(n) WHERE n = 5 = 5`.

## Explicit boundary

Scalar aggregate state now streams; **grouped** aggregate state (many GROUP BY
groups), joins, window functions, and final result assembly still materialize
and remain the Phase 5 gap. The adversarial sort/join/group gate stays open.
