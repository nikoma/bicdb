# Registered remote native-image catalogue floor

This is a source implementation and focused regression design based on
`d6908095e0d347e563ef68801f49e52dba35452d` (source 1.0.494-beta). The new
adoption code and four new controls have not yet been compiled or executed.
Earlier native-base and row results do not qualify this successor.

The original Registered receiver can now request `AdoptCatalogueFloor` after
its own `RegisteredRemoteBasePublication` has produced a verified actual
`NativeInstalledRangeImageBase`. The host borrows that actual retained object,
the original native-base boundary, protected final-image receipt, Installing
fence and A lease. There is no remote-DATA conversion to local source lineage,
a local image-install fence or a verified local install.

The new mutable service sink is
`distribution_data/registered_remote_catalogue.rs`; the publication is
`distribution_range_consensus/native_image_base/registered_remote.rs`. Before
mutating memory or touching the file, the original host retains both the exact
old catalogue and the exact candidate. The candidate sets only the selected
range's `last_index`, `resolved_through` and `compacted_through` to the actual
verified image's R, clears that covered log, and inserts a
`NativeImageCatalogueBase` bound to its actual native receipt checksum. Existing
local-log validation refuses a higher unresolved or irreversible tail.

Before first retention, the existing full current-final-image checks run under
the actual original context, including the completed mutable history and row
headers. Every continuation acquires fresh authenticated Finished, Role and OWN
observations, and the actual hook/admission/native-journal/freeze guards. It
checks original MStore, Store slot, DB open, native birth, catalogue UUID and A,
the original protected proposal, exact base/final archive mapping, current image
generations/schema/readers/namespace IDs/index definitions and B visibility and
durability. OWN term and index cannot precede the final-image publication.
The installed-final helper supplies necessary constraints; it grants nothing.
Prunable stage headers are not reconstructed as current authority.

Ordinary admissions retain their strict catalogue checks. Only an opaque
original adoption publication can admit its exact old or candidate catalogue
to the re-fsync sink. Every attempt, including a retry after apparent rename
success, calls actual `replace_durably` with file and directory fsync. An error
retains the exact candidate and persistence uncertainty. The sink clears
uncertainty and publishes progress only after successful fsync, exact disk
readback and original-owner postchecks. A matching pointer, memory snapshot or
visible renamed file is insufficient.

The focused selector is
`native_registered_fifth_remote_catalogue_floor_actual_`. Its four genuine
receiver controls exercise positive native/catalogue binding, refusal without
the original verified base, two consecutive actual post-rename directory-sync
EIOs followed by the same-candidate retry, and cancellation after actual fsync
followed by fresh same-A/same-native-base continuation. They preserve the
original Manifest/frame journal and record logical states, raw catalogues,
native receipts and exact fault responses for independent reconciliation.

CLOSED, Installing, image-install intent and every other range remain intact.
This does not create NEW, a global decision, Open, Ready, a writer or Serving.
There is no cold-owner reconstruction, source retirement, physical fault-safe
four-to-five-node rebalance, bounded convergence or throughput result. The
cap-eight source/OLD lifetime gate, independent index/FTS parity and larger-data
qualification remain open. Existing raw custody files are guarded live-owner
stable copies followed by cleanup, not stopped or atomic power-loss snapshots.
