# TPC-C Performance Ledger

> Publication note: infrastructure identifiers and machine-local paths are
> anonymized examples. See [source distribution notes](source-distribution.md).

Central record for pgwire/embedded TPC-C performance experiments. Use this file
to decide whether an idea is kept, rejected, or needs a repeat.

For the full benchmark operating procedure, branch discipline, tmpfs cleanup
rules, DSUM calculation, and remote build/run commands, see
[`tpcc-performance-playbook.md`](tpcc-performance-playbook.md).

## Gate

- Benchmark host: `benchmark-primary` (`192.0.2.10`), tmpfs (`/dev/shm`).
- Metric: district-sum NOPM, computed as `delta(sum(d_next_o_id)) / minutes`.
- Seed discipline: restore a clean tmpfs seed before each measured run and clean
  trial datadirs after every run.
- Pgwire keep gate: an experiment must beat the latest `main` baseline by a
  meaningful margin and should clear the historical 125k+ NOPM line before it is
  considered worth keeping.
- Keepers must be generic database improvements, not benchmark-specific
  shortcuts. TPC-C/HammerDB is a stress harness used to expose bottlenecks; rows
  that skip required writes, bypass validation, special-case table names, or
  weaken recovery/MVCC semantics are diagnostics only even if they clear a
  throughput line.
- `Decision=reject` is scoped to this TPC-C pgwire gate. Some rejected ideas may
  still be useful for other workloads such as chat, read-heavy APIs, lower
  contention writes, large result streaming, or latency-sensitive workloads; note
  those separately instead of deleting the evidence.
- Current latest-main baseline/gate: about 119k DSUM NOPM, with the best
  reproduced clean `26cc25e` default run at 119,721 on a 2 min + 1 min ramp
  run. Treat isolated lower draws as diagnostic noise unless they reproduce.
- Current valid pgwire high-water: 419,228 DSUM NOPM on `e0d0aab` (thin LTO, attempts=2) (perf/row-conflict-recheck; collection-guard hoist, attempts=2)
  binary with stable blocking pgwire, READ COMMITTED update/delete recheck,
  PL rollback, PL/pgSQL `INTO` no-data diagnostic, sharded indexes,
  pgwire simple-CALL fast path, and `BICDB_RC_UPDATE_LOCK_ATTEMPTS=4` at VU32 /
  `MAX_ACTIVE_WRITES=24`. The same attempts=4 setting also produced a 248,931
  third run and one lower 233,924 repeat; the strongest reproduced band so far
  is 239k-250k across attempts 4-8.
- Current working target: at least 300k NOPM; Postgres reference is roughly
  600k+ NOPM on the same host/harness.
- 2026-07-01 benchmark-primary post-outage health check: `/dev/shm` was empty with 47G free,
  root ext4 had 3.2T free, memory had 91G available, swap was essentially
  unused, SMART overall health passed with no media/data-integrity errors, and
  current-boot kernel logs showed no OOM, hung-task, ext4, or NVMe timeout
  errors. One stale `bicdb-ab.service` was failed but no benchmark process was
  active.

## Cross-Workload Interpretation

These classifications are not keep decisions for the TPC-C pgwire gate. They
preserve ideas that failed this hot-row, exception-heavy HammerDB shape but may
still be useful elsewhere.

Rule for future rows: `reject for TPC-C` only means the idea failed the current
HammerDB pgwire throughput gate. Mark an idea as `design lead` when it improves
a generic mechanism, reduces conflicts/latency, helps read-heavy paths, or fits
chat/feed/counter-style workloads even if it misses DSUM NOPM here. Only mark
`reject` with no qualifier when the idea is incorrect, unsafe, or broadly slower
for the mechanism it touches.

| Idea family | TPC-C pgwire result | Other workload fit | Notes |
|---|---:|---|---|
| Lower active writes / lower VU counts | mostly 80k-115k | Lower-contention OLTP, chat APIs with smaller write fan-out | Cuts conflicts but underfills TPC-C. Worth testing when latency/p99 matters more than max NOPM. |
| Longer row-lock waits | 39k-90k | Latency-sensitive same-row updates with user-visible retry cost | Reduces serialization failures, but serializes TPC-C hot rows and loses district progress. |
| Admission read/query tuning | up to 119k | Mixed read/write services | Near-baseline and lower conflict counts; may smooth production tail latency even without raising NOPM. |
| Pgwire response batching | about 100k | Large result sets, chat history fetches, analytics-ish reads | Not a TPC-C bottleneck because procedures return tiny responses. Still relevant for large pgwire result streaming. |
| RowId fast path | default required; off gives 92k | Point-lookups and feed/message fetches | Keep default on. Attempts to broaden generic RowId loading hurt TPC-C, but the existing path is valuable. |
| RowId-native primary-key prefix lookup | 75k-159k | Composite-key prefix reads, feeds, tenant-scoped listing APIs | First run was the best post-baseline lead, but repeats showed conflict amplification. The lookup idea is useful; TPC-C needs a conflict-control partner before it is keepable. |
| BTree index store | about 115k | Read-heavy or lower-write-contention services | Close to baseline and fewer conflicts in some runs; combinations with high write pressure collapsed. |
| Adaptive routine/WASM path | 87k-100k | Compute-heavy stored procedures after more maturity | Increased raw procedure/query volume in one run but lost useful district progress. Not the next TPC-C lever. |
| Grouped fetch/release/index-scan reductions | 66k-114k | Workloads with larger batches or many touched rows per request | Micro-optimizations can raise raw throughput but may perturb conflict timing badly in TPC-C. Re-evaluate with representative chat/feed shapes. |
| Additive hot-row conflict merge | 64k-94k | Counters, likes, unread counts, append-only metrics | Generic commutative-update support is still conceptually valuable, but the attempted commit-rebase shape was not safe/effective for TPC-C. |
| Allocation-free pending-write checks | 66k-120k | Transactional reads with many indexed lookups and few pending writes per table | Avoiding cloned pending-id vectors is generic, but the TPC-C repeat was unstable and conflict timing dominated the small allocation win. |
| Internal retry after handled routine `40001` | 75k | Background jobs or idempotent procedure runners | Retrying no-progress handled serialization failures inside pgwire lowered late conflict count versus the worst collapses but cut useful TPC-C throughput. Semantics are too broad to keep without a narrower contract. |
