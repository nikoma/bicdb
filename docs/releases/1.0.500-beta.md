# 1.0.500-beta: receiver recovery ordering and authorized restore of copied stores

Recovery of a receiver now rewrites and syncs its log before it persists the
completed origin mapping, so a crash between the two can no longer publish a
mapping whose log is not durable.

A native store refuses to open from a plain copy of its directory. This version
adds the authorized ways to move one:

- `bicdb backup adopt-copy <source> <target>` authorizes an offline cold copy
  after verifying the source holds custody;
- backup restore, standby bootstrap and branch copy leave an authorization for
  exactly the directory they created, consumed by its first open.

A plain copy of a restored directory is still refused.

Also fixed on this lineage: a promoted node can resolve a rename undo journal
replicated from the previous primary; rename inside an open transaction on an
uninitialized database; ROLLBACK after a transactional DROP TABLE; renaming a
partitioned parent with attached children; ROLLBACK after a failed statement
that follows a rename.

Limits: receiver provenance is carried in-process only (no authenticated wire
carriage, no peer authentication); custody records are unkeyed checksums, so
they stop plain copies, not an actor with write access; a restore does not
retire its source.
