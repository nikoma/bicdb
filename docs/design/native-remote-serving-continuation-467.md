## Metadata provenance

`NativeFirstCertifiedHistory` has a private constructor on the original actual
metadata owner. It requires its retained genuine opaque dual-durable proof and
typed successful metadata proposal return, exact candidate and term/index, and
a distinct actual committed OWN/native-MStore observation. The latter compares
the complete selected native handoff record, configuration and member
birth/credential/schema bindings. Unrelated range load/topology changes may
remain in the actual committed head. Compacted metadata logs do not prove that
the earlier issued entry itself committed; the selected effect is observed
against the retained actual proposal and genuine data proof. A record-only historical response
does not create that owner; cold reconstruction is refused. Stop revokes the
owner before any fallible listener/worker shutdown.

`NativeRemoteMembershipScope` is borrowed from that owner. Its candidate is
produced by the exact original manifest/decision builder, independently of old
frame or Pending request liveness. The metadata-store entry checks that exact
owner-built candidate. The final bounded request check follows allocation and
validation, before authority invalidation and proposal effects. Successful
typed returns are retained before postchecks. An unknown proposal return is not
reconstructed from visible topology bytes or blindly proposed again.

Both metadata steps remain frozen. No new public record-only promotion helper
exists. Existing generic trusted `MetadataConsensusStore::propose_topology`
behavior is preserved; its structural checks do not independently prove a data
quorum. The recipient phase consequently needs actual durable-D/catalogue
reobservation as well as its fresh actual metadata witness and physical owners.

## Fresh phase and transport boundary

`NativeJointServingPhase` is appended to the existing request-purpose enum. It
names the exact committed AwaitingActivation session, nonce, decision and current
activation configuration. Effectful requests require the actual current range
or metadata leader and final-voter recipient. Readonly observations may be made
by final voters, the explicitly retiring source, or metadata leader. They cannot
enter native effects. Existing CommittedHandoff/Pending and CurrentJointRecovery
semantics are unchanged. Old readers reject the unknown purpose/request.

The new Serving wire request/response variants are appended. Authenticated
dispatch moves the actual peer value into the existing original INITIAL or
Registered owner, which independently acquires fresh Role/OWN/MStore and finds
its retained native phase before queueing. It creates no missing phase or host.
The generic service path refuses requests without that before-latch owner;
Joined does not acquire INITIAL source admission. The explicit mutable-owner consumer now handles preparation and distinct
known-only preparation readback; bridge/Open/release/policy consumers remain
incomplete. Queue admission alone cannot complete an operation or establish
Serving.
The new RPC client creates `AuthenticatedNativeRemoteServingFrame` only after
actual pinned mutual TLS/native-birth, exact request/response and current
metadata validation. It retains compact bounded facts and the original request
token, rather than repeated manifest encodings. Decoding DATA creates no frame,
local quorum, preparation, Open, writer, or release admission.

The participant-owned queue holds one original outstanding request. It preserves
the admitted mutation watermark and refuses equal/older sequence, rebinding,
concurrent work and mutations after an unresolved effect. Readonly work cannot
change that watermark or resolve unknown durability merely by returning DATA.
An effectful error retains the actual original request, hash, absolute ingress
deadline and error class. Returned-history accounting is bounded and does not
replace the primary API result. No old request deadline is reset.

`ObserveDecision` has a direct actual-recipient read path, so a serialized host
owner need not wait for its own queue while collecting fresh physical facts.
Its private admission borrows the original known native attempt and completed
receipt, checks exact CURRENT/archive/status/provenance and the actual DB/Store
open, and observes the original successful owned catalogue under fresh actual
Role/OWN/MStore. Original OLD uses its retained predecessor, hook, native
journal, promise and Frozen; Registered uses its actual original exclusion
scope. No WAL is replayed, uncertainty cleared, old Pending role renewed or
local quorum constructed. This initial read uses original owners; after
retirement, later phase observations need the actual successor owner.

The metadata-owner control calls that real pinned-TLS path for the union of
original OLD and final NEW after actual AwaitingActivation. The source control
requires the actual OLD-union-NEW recipient count (not a hardcoded five)
and unchanged target native/catalogue evidence. It is uncompiled and unexecuted, and does not establish Serving.

## Actual recipient preparation consumer

The actual serialized `NativeMetadataControlHost` consumes the authenticated
queue through `poll_finite_remote_serving`. It retains the same original
participant, process, lease and native attempt before entering any preparation
helper. The INITIAL survivor route uses the existing actual CLOSED transition
and transfers its real lease; Registered uses its original target owner. No
Installed/Joined owner is cast to either route. The metadata owner's
`drive_finite_remote_preparation` retains its privately allocated operation and
original request before a real pinned-TLS call, services its own actual host
queue while waiting, and saves the actual return before postchecks. These are
explicit finite methods; they are not called by an automatic scheduler.

`NativeRemoteJointPreparationAttempt` retains the issued native XID at the real
transaction callback entry, its exact candidate before puts, and the actual
native API return before cancellation, physical readback, pin acquisition or
outer checks. An error retains its class plus a bounded 4096-byte formatted
prefix, full formatted hash and completeness flags. This does not retain an
unbounded error object. Native entered/put/IO-error outcomes remain unknown and
cannot select another transaction. The original helper return is never rewritten
as successful by a later read.

`ResolvePrepared` is a distinct authenticated readonly request. It can resolve
only the same original participant/peer/operation's retained known native
commit, after fresh Role/OWN/MStore and exact native CURRENT/archive/status,
DB/Store/Frozen, original private D/catalogue and physical-history checks. It
uses no transaction, Controlled permit, format write or replay. Successful
readback can produce a new preparation receipt; it does not prove a failed old
fsync succeeded. Once a genuine completed physical owner and its one pin exist,
the host retains them before later checks. Ordinary observation DATA cannot
clear the queue's unknown mutation; the distinct resolver requires that exact
private attempt and actual completed owner. If no CLOSED transition/lease was
successfully transferred, or the original native return is unknown, it refuses.

Every effect remains bounded by the original server ingress window, its Role,
OWN cancellation/deadline and original host process. The retained process is
captured from the actual host lifecycle and weakly binds the real participant
and service; it cannot revive a finite request or keep a stopped host current.
Subsequent readback uses a genuinely new authenticated request and fresh
metadata observation, retaining the same original native attempt and lease.

The protected read splits full domain/topology/hash validation outside the
short final version guard from memory-only lifetime/version checks inside it.
`catalogue_decision_sha256` labels the original successful decision candidate;
`current_catalogue_sha256` separately labels the actual current healthy whole
head read. They need not be equal after lawful unrelated selected-head changes.
Neither digest is an authority constructor.

Three added normal-host source controls are
`native_first_remote_registered_prepare_uses_actual_owner_and_tls_caller`,
`native_first_remote_prepare_actual_postcommit_server_cancel_known_read_no_replay`,
and `native_first_remote_prepare_actual_commit_sync_unknown_cannot_be_read_as_success`.
They extend the existing genuine FIRST/native-D/catalogue/Certified setup.
The cancellation control requires a live original server/Role/OWN at the real
known native-return cut, then checks fresh same-attempt readback without XID/LSN
change. The sync fault must actually fire and remains unresolvable as success.
Original outcomes and diagnostic failures are recorded before assertions. All
three are **not tested**: no compilation/runtime/race result exists. Earlier
setup failure must remain a failure/unreached cut. The new positive covers the
Registered target, not every OLD survivor or full Serving.

## Remaining owning integration

The complete consumer chain is still absent: actual ALL-new preparation
aggregation, native bridge, owned catalogue Open, ALL-release and first policy
must follow the actual physical owners. No decoded frame becomes a local quorum.
The original 1.5-second OWN, five-second request and two-second SDK controls in
prior suites have not been widened, and this component does not establish that
their original timing failures are fixed. No new full-Serving result is claimed.

Before unique release, obsolete remote OLD observation and target Frozen
references must transfer one way under a genuine fresh ALL-new-Open proof.
Survivors drain obsolete references while retaining their actual runtime;
the retired OLD member remains CLOSED for later cleanup and is never released
as a new voter. Donor certificate retirement is a separate RAM-only custody
transition, not a row/native-WAL cleanup or a final-voter role cast.

There is also a source-confirmed listener handoff dependency. The current
Registered policy path calls `drain_for_assigned`; later Joined transfer drains
the Closed listener. `ClusterDataServerHandle::stop_and_drain` waits for every
active connection. A queued policy RPC waiting on the very same listener cannot
synchronously drain itself. The implementation must provide an actual safe
response-only tail/drain handoff or independent authenticated control ingress;
it must not decrement active guards prematurely, label queue acceptance
Serving, or run effects after the original server window expires. This is not
an executed deadlock reproduction or an RTO result.

## Actual remote prepared collection and native bridge child

A separate successor adds an explicit recipient-owned `PublishBridge` consumer.
The same host retains its actual completed preparation, process and Frozen
lease. It fetches `ObservePrepared` from **every** final NEW member over its own
pinned authenticated transport; no coordinator vote list can construct
`NativeRemotePreparedQuorum`. Its local observation is also a real TLS exchange.
The readonly listener reaches only a weak reference installed from the actual
host-retained preparation; it cannot reconstruct an ended owner. That direct
readonly path prevents an actor from queueing behind itself while collecting.

The complete collection binds the same MF, phase, D, peer incarnation, native
DB/Store opens, local native D receipt/provenance, original Frozen owner and
preparation. Only after collection does the recipient acquire a distinct fresh
actual OWN/MStore/local physical observation. The remote admission retains those
opaque values and the original authenticated effect request. It releases only
this recipient's own preparation read pin; the actual lease remains retained.
Existing local prepared quorums and local activation constructors are unchanged.

The native bridge writer uses the existing protected record/immutable archive
format and full local prepared publication scope, retaining original phase
owner, actual native history and current MStore checks. A host-retained private
attempt captures the exact original DB/Store/Frozen/range/D/preparation before
entry, the real issued XID before callback checks, candidate before puts, and
actual native API outcome before readback or outer checks. Actual native errors
remain unknown; a missing/current visible record never authorizes a second
transaction. The successful bridge receipt is retained before later request or
wire checks. The final reported native bridge point is independently reread
under a lexical physical scope through the memory-only metadata guard.

`native_first_remote_all_actual_preparations_then_target_native_bridge` uses
the retained five normal host objects and actual TLS, including the genuine
INITIAL survivor preparation path and Registered target. It requires the
actual bridge native transaction to have returned known, the exact native
CURRENT/archive to match, the original preparation to remain unchanged, and
no catalogue Open/release/writer installation. The separate
`native_first_remote_bridge_refuses_actual_unprepared_final_member` omits an
actual final member's preparation, still requests the real target bridge, and
requires its authentic refusal, no entered bridge attempt and no bridge CURRENT.
All API outcomes and diagnostic failures precede assertions. These are test
**definitions only**: compilation, actual cut reach, runtime and races are
**not tested**.

Lost/failed bridge calls retain the original native attempt and coordinator
request; the mutator is not blindly reissued. A native known-only read helper
exists, but a distinct same-original authenticated bridge-resolution consumer
is not connected yet. Such an unresolved bridge remains safely blocked; this
is not a bounded recovery claim. The native bridge positive does not establish
catalogue Open, ALL-new release, policy installation, native majority leadership
or any post-release SDK ACK/Strong result. The existing SDK and timing
assertions remain intact and must execute on the final composed source.

## Known original bridge resolution on the current-source integration

The current-source successor connects `ResolveBridge` as a distinct readonly
operation. The actual host retains the original private bridge attempt and
same prepared owner before entry. A fresh authenticated request re-collects
actual ALL preparations and independently reads current OWN/MStore plus exact
native CURRENT/archive/body under the same DB/Store/Frozen and process binding.
The read admission is a different type from the effect admission; native WAL
publication cannot accept it. It creates no transaction, Controlled permit,
format write, catalogue mutation or new native attempt. A genuine successful
read is retained before its outer checks, while the original native API result,
issued XID, candidate and error details stay unchanged.

Only the same actual peer/incarnation/certificate, privately allocated original
operation, phase and MF may resolve the pending bridge reply. The queue clears
only that original PublishBridge result after the protected known read and
final memory checks. Ordinary `ObserveBridge` DATA does not clear it. Resolving
one known native effect does not clear global catalogue uncertainty or produce
Open/Serving permission. A missing attempt, native entered/unframed/API-error
outcome, changed context or expired original request cannot be reconstructed or
replayed. The next read owns a new request; it does not make the old one live.

Two added definitions use the existing real five-object/TLS ALL-preparation
setup. `native_first_remote_bridge_postcommit_server_cancel_resolves_same_native_xid`
requires the actual bridge native API to return known, then deliberately cancels
its real original server token while original windows are still live, before
receipt/postchecks. It requires a refused mutation replay and fresh readonly
resolution with unchanged candidate, XID, next-XID/LSN and native CURRENT/archive.
`native_first_remote_bridge_commit_sync_unknown_remains_blocked` requires the
actual commit-sync fault to fire and the original native result to remain
unknown after the fresh reader refuses; visible bytes are never success proof.
All returns and forensics precede assertions. No post-fault APP or rollback/no-effect
claim is made. Compilation, runtime, cut reach and races are **not tested**.

This successor runs only in a separate source worktree based on the exact
current 520 integration. It keeps the existing typed owned activation and all
catalogue IO generation writers as the sole future Open sink. The earlier
2ad6 checkpoint's missing bridge resolver is superseded by this implementation,
not by a new claim about its unexecuted tests. Full Open, ALL-release, policy,
leader/SDK acceptance, controller, cold recovery and GC remain open.
