# 1.0.521-beta: a range move across five separate processes

1.0.520-beta is reserved by a parallel candidate and is not used here.

1.0.519-beta added the first pieces of a cross-process range handoff. This
release completes the route: one operator command moves a replicated range
onto a fifth node while every member runs in its own process. It is an early
operator feature with real limits, listed below. Read them before using it.

## What is added

- **Operator commands.** `move-range` starts a move and `transfer-metadata-leadership`
  makes the metadata leader coincide with the range leader, which a move
  requires. The host status reports the move's stage, what it is waiting for
  and, when blocked, the member responsible.
- **Remote backend, complete.** The coordinator drives every stage over
  authenticated requests: readiness check of all members, source cut, image
  install on the target, decision round, the three membership commits,
  bridge preparation, publication and opening, custody retirement, release,
  writer policy, target serving, activation record and source retirement.
  One call walks a move to `Completed`; a restarted coordinator resumes from
  committed metadata.
- **Member steps.** Each member performs its own local work when asked,
  under its own freshly acquired role and its own reading of metadata.
  Requests carry identities only; no role, quorum or certificate is accepted
  from a request.
- **Certified scope in the committed record** (record version 2), so the
  promotion and final membership commits no longer need the decision proof
  to be re-collected after a restart.
- **Five-process acceptance test** in the CLI test suite: five hosts, a
  client appending and reading the moved range, the move to completion, and
  a check that every acknowledged append is readable afterwards.

## Review fixes included

- A decision is certified only when every new member and the retiring source
  hold it durably. A majority-only round could have stranded the range.
- All members are asked for readiness before the learner allocation is
  committed, and an abort before the cut works for a remote coordinator.
- An abort no longer reports "nothing committed" while a proposal of this
  host is undecided.
- A leadership transfer is refused while this host's move is unfinished.
- A reused or skipped operator sequence number is refused without ending the
  host; errors of a move step are reported.
- Members bind a step to the certified scope before keeping anything, release
  finished entries, and report "released" only after confirmation.

## Limits

- **The moved range is unavailable during the move.** Strong reads and writes
  on it are refused from the learner allocation until the target serves:
  22 to 46 seconds in three measured five-process runs. No acknowledged write
  was lost.
- **Do not start a move while clients write to the range.** A write in flight
  when the allocation commits makes the coordinator refuse the cut; the abort
  then works. A second move after such an abort was seen to block at the
  source cut with the range refusing reads and writes and no abort possible.
  Under client traffic members can also answer "busy" until the coordinator's
  bounded repeats run out.
- Nothing after the source cut can be aborted, and a member crash after the
  cut is not survivable for that range (no data is lost; the range stays
  unavailable). Original members cannot restart; only learner hosts can.
- A member that is down during the decision round stalls the move.
- The coordinator must be both the metadata leader and the leader (and
  retiring source) of the moved range.
- The same range cannot be moved a second time.
- Retired source rows are not physically removed.
- The new requests and record version 2 are not compatible with older
  binaries; do not mix versions in one cluster.
