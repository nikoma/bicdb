# Native range catalogs require their own fsync policy

**28 distinct focused tests passed on private source `574ea56074a991368e9dae2129a0734a23bc1be3`, package `1.0.471-beta`.** Six are new native configuration controls; the remaining 22 are affected read, origin, mTLS and embedded Apply controls on the same compiled source. This does not describe a public merge, release binary, deployment or production qualification.

Source inspection of `18723cf4` and `6d07ded1` found a reachable configuration gap: an actual native factory database required fsync, but a fresh format-3 `RangeWriteStore` could independently be opened by `ClusterDataNodeService` with `fsync=false`. The ordinary Prepare/Commit/Certify path forwarded that separate flag to `storage::write_atomic` and did not reject it. The existing format/uncertainty check was not an fsync check. **No pre-fix crash experiment or observed acknowledged data loss is claimed.** This is not attributed as a cause of the older Azure failures. A readonly fact by itself was never a durability grant.

The corrective source checks actual database root/open and persisted native reader-format policy before opening learner/range/digest stores. Native catalogs require fsync and the same physical database root. Native ACK, ordinary Apply and local-read proof paths repeat the appropriate actual store policy; source admission uses its actual borrowed DB context without reacquiring the outer DB lock. The format flag is reread, so a service opened before real activation cannot keep an async native CQ path. These checks establish necessary local durability configuration, not a birth, quorum, physical range floor or strong-read permission. Permission and TLS policy are unchanged.

The six configuration cases exercise:

- Native-born database plus async service: refusal before any range/learner/digest catalog or native-floor change.
- Healthy fsync service: actual RF1 coordinator, ordinary row/WAL commit ACK, native R1 and local observation remain available under the real outer database guard. No remote ACK is fabricated.
- A separate native catalog root: refusal before creating catalogs in that foreign directory, preserving its canary.
- Lower native write/read-proof paths: explicit false-sync refusal without mutating the native floor or catalog.
- An already-open legacy async service: real provisional Prepare/Commit succeed, then actual sticky format activation causes Certify to refuse; the prior catalog bytes and provisional state remain unchanged. A format flag alone creates no native birth.
- Explicit legacy async operation: Prepare/Commit/Certify remain supported while the native format is absent. This is preserved legacy behavior, not a production durability claim.
