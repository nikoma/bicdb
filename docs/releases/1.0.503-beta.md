# 1.0.503-beta: authenticated principals and application locking reads

This candidate combines two ERP runtime corrections on merged 1.0.502-beta
source, revision `629857f5eaaeee5f5a9124d505406d8cd6a29535`. It preserves
that source's receiver recovery, conditional native-origin custody and merged
HA diagnostic-latch and fifth-member data-path changes. Their presence does not
establish broad HA qualification for this ERP candidate.

## Exact authenticated subjects

The signed `authenticated_principal` application feature enables the typed,
zero-argument `auth.current_principal` builtin. Its result carries the exact
verified actor subject, effective roles and scopes, tenant and workspace. Subjects
are strings: opaque identifiers and numeric-looking text retain their identity.
The existing `auth.current_user` behavior and persisted numeric actor fields are
unchanged. Anonymous calls are refused; caller request fields cannot supply the
principal. Service calls continue to use the existing propagated actor.

Package admission requires the feature and exact builtin signature, including its
record result, no arguments, no method and no projection. Cell refuses this
feature explicitly: ordinary native support does not establish Cell support.

## Snapshot locking reads

After an application transaction obtains a row lock, repeatable-read and
serializable transactions reject a row changed since their snapshot before
returning it to application code. A conflict reported only after a provider
callback has already observed a stale row is insufficient. Read-committed locking
reads retain fresh committed visibility. A transaction's own pending insert or
update remains visible under its lock.

Immutable-reference upgrade refusals now include bounded contract identifiers
and guard names, without expressions, row values or actor claims. Their original
admission rule remains enforced.

## Qualification and recovery scope

The Node SDK principal fixtures and source-authored locking fixture exercise
strict ABI admission, authentication and tenant boundaries, lock contenders,
forced termination and closed-store recovery. Their results must identify the
actual binary hash; passing an earlier candidate does not qualify this source.
This release note records candidate behavior, not completed ERP or Hub acceptance.

Cold copies use the official `bicdb backup adopt-copy SOURCE TARGET` operation
while both stores are closed. Native-origin custody is conditional on actual
activation of `native_origin_root_v1`; ordinary standalone stores may remain
inactive, for which `NotRequired` is valid. Activated stores retain plain-copy
refusals and require genuine source custody. Qualification must preserve source
bytes and must not manufacture activation flags, roots or authorizations.

No new binary, production release, deployment or broad HA qualification is
implied by the source version. The existing ledger and posting schemas are not
reimplemented or expanded by this change.
