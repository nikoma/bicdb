# BicDB 1.0.500-beta

Authorized application row locks now apply the same post-acquisition committed
version check as SQL locking reads. A repeatable-read or serializable
transaction whose target changed after its snapshot fails before its action
can continue with the stale row. Read-committed refresh and a transaction's own
pending inserts/updates retain their existing behavior.

The existing actor, tenant/RLS, lock acquisition, rollback and commit boundaries
are preserved. This change does not weaken posting locks or retry/deadline
limits.

A portable Node/Carrier fixture records the actual after-lock callback, rather
than treating a later commit409 as sufficient. It covers all three isolation
levels, denied lock POSTs, own pending writes and process/cold recovery. Source
and fixture preparation are separate from qualification of a built artifact;
no stock-timeout or complete ERP qualification is implied by this source note.
