# BicDB 1.0.320-beta

This release completes Phase 3 of the industry-agnostic BicDB
Cell/Application Architecture: one cryptographically bound Cell can now load a
signed backend and frontend application, perform device-bound identity
handoff, and issue Cell-local host-only sessions. Regulated-data admission
remains closed.

## Cell-native application authority

- Application packages now sign exact frontend byte hashes and component
  contracts covering execution scope, data class, capabilities, egress, and
  database features.
- The Phase 3 construction path requires every component to be Cell-scoped,
  match its manifest pin, request no regulated data or egress, and declare an
  exact authority union matching executable package surfaces.
- Raw SQL, ambient secrets, blobs, egress, and incomplete providers are refused
  before database open. HTTP routes and frontend assets require corresponding
  signed backend/frontend components.
- Required RLS, stored-function, trigger, and job features are derived from the
  package surface, must exactly match signed declarations, and must be covered
  by a manifest-pinned certification for the exact BicDB binary and database
  format.

## Identity and session boundary

- A manifest-pinned Cell authorization policy defines enabled members,
  devices, roles, scopes, assurance, session lifetime, and authorization epoch.
- A short-lived OIDC Ed25519 assertion must bind the CellId, device, nonce, and
  one-time assertion id; the device must prove possession of its Cell-local
  Ed25519 key.
- External roles and scopes are discarded. Final authority comes only from the
  Cell-local policy.
- Session keys are HKDF-derived from Cell key material, CellId, manifest
  digest, and authorization epoch. Sessions use a secure, HTTP-only,
  same-site, `__Host-` cookie.
- Consumed handoff ids are persisted as HMAC-authenticated hashes in a bounded,
  fsynced journal and remain rejected across restart.
- Ambiguous Authorization-plus-cookie credentials and duplicate session
  cookies fail closed. Raw authorization, cookie, proxy-authorization, and API
  key values never enter Carrier or raw WASM guest requests.

## Same-origin frontend

- The trusted Cell host serves only frontend bytes embedded in and covered by
  the signed package. There is no ambient filesystem or CDN fallback.
- Digest-pinned immutable asset paths, exact content types, strict CSP,
  `nosniff`, frame denial, no-referrer, restrictive permissions, and
  same-origin opener/resource policies are host-owned.
- Application responses cannot set cookies, transport headers, or weaken
  host-owned security headers. Trusted and application responses remain bound
  by host response-size and header limits.

## Runtime and operator surface

- Phase 3 adds coherent `phase3-cell-native-*` manifest profiles plus pinned
  authorization-policy and feature-certification digests.
- `bicdb cell serve` and `bicdb-cell serve` accept
  `--authorization-policy` and `--feature-certification`; they must be supplied
  together with the existing release, identity, and deny-all egress policies.
- `BICDB_RUNTIME_MODE=cell` supports the equivalent
  `BICDB_CELL_AUTHORIZATION_POLICY` and
  `BICDB_CELL_FEATURE_CERTIFICATION` environment paths.
- Runtime and JSON status use the industry-neutral
  `regulated_data_admission`/`regulated_data_admitted` terminology. Legacy
  `phi` data-class spellings remain read-compatible aliases, while canonical
  output is `regulated` or `regulated_local`.

## Validation

- full signed-package frontend/component tamper tests;
- exact capability and database-feature contract negative tests;
- persistent one-time handoff replay and device-proof tests;
- local-authority replacement and host-session verification tests;
- credential-withholding and ambiguous-cookie tests;
- full `CellRuntime::open` acceptance path using a signed manifest, attested
  one-cell key lease, encrypted database, signed backend/frontend package,
  pinned policies, application activation, HTTP listener, and frontend fetch;
- complete Cell, application-runtime, CLI, workspace compile, formatting, and
  repository-invariant suites.

## Admission remains closed

Phase 3 is callable and can host an industry-neutral application in one Cell.
It does not complete threshold fleet activation, Cell-scoped HA, hardware-bound
device replicas, cross-Cell grants, deployment-level confidential-compute
attestation, external data-commit rollback roots, independent feature evidence,
or independent regulated-workload review. The runtime truthfully reports
`regulated_data_admitted = false`.
