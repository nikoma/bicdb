# BicDB 1.0.2-beta

Release date: 2026-07-31

BicDB 1.0.2-beta closes P0-1: security identity used by RLS and protected
mutation paths is now host-authenticated connection state, not client-mutable
SQL session state.

## Security changes

- Authenticated pgwire users can be assigned stable user, client, tenant,
  workspace, role, and scope attributes in the server user catalog.
- Every successful password or SCRAM authentication creates a distinct
  connection `SecurityContext` and unpredictable session id.
- Carrier security attributes remain readable through `current_setting` for
  existing RLS policies, but `SET`, `SET LOCAL`, `RESET`, and `set_config`
  reject attempts to change them with SQLSTATE `42501`.
- `current_trusted_tenant()` returns the host-authorized tenant, or `NULL` when
  the invocation has no tenant authority.
- Transaction snapshots, savepoints, prepared statements, concurrent query
  workers, describe execution, cluster database DDL, session reset, and pooled
  GUC-state restoration all rebind the immutable connection context.
- `RESET ALL` and `DISCARD ALL` preserve trusted identity. `DISCARD ALL` clears
  untrusted application GUCs, cached catalog state, portals, and prepared
  statements.
- MutationGrant-derived core contexts now carry workspace, roles, and scopes;
  administrative bypass audit events include the full trusted identity and
  authentication strength.
- Client-modified JWT tenant claims fail signature validation before an actor
  context is created.

## Operator action

Create tenant-bound pgwire users with explicit identity attributes:

```sh
bicdb user create alice \
  --password "$ALICE_PASSWORD" \
  --path /srv/bicdb \
  --user-id alice \
  --tenant tenant-a \
  --workspace clinic-1 \
  --role clinician \
  --scope patients:read
```

Existing password users continue to authenticate, but receive no tenant
authority until the operator assigns an identity. Tenant-protected reads and
writes therefore fail closed after upgrade instead of trusting legacy Carrier
GUCs.

Bind an existing login without rotating its password:

```sh
bicdb user bind-identity alice \
  --path /srv/bicdb \
  --user-id alice \
  --tenant tenant-a \
  --workspace clinic-1 \
  --role clinician \
  --scope patients:read
```

## Compatibility note

Applications must stop issuing `SET carrier.current_*` or `set_config` for
security context. Trusted Rust hosts should create `SecurityContext` values;
pgwire deployments should store assignments with `create_user_with_identity`
or the `bicdb user create` options above. Ordinary dotted application GUCs are
unchanged.

## Embedded application SQL

- ABI-v2 applications can declare checksum-bound bounded SQL with exact typed
  parameters/results, relations, routines, database actions, and affected-row
  limits. The runtime independently parses and verifies every declaration.
- Embedded SQL executes through BicDB's in-process engine inside the owning
  application transaction. Carrier resource contracts receive a typed SQL
  catalog projection without a pgwire connection or generated repository.
- Signed SELECT/grouping/aggregates, INSERT/UPDATE/conflict-upsert/DELETE,
  scalar and table-returning SQL functions, declared native functions, and SQL
  procedures are supported. Protected DML and its read-committed row-lock
  rechecks require host-issued transaction-local `MutationGrant`s.
- Dynamic or multi-statement SQL, DDL, undeclared relations/routines/actions,
  type disagreement, and statement hash disagreement fail closed.

## Embedded application transactions

- ABI-v2 applications can begin read-committed, repeatable-read, and
  serializable transactions. Repeatable read uses BicDB's fixed MVCC snapshot.
- Serializable transactions record relation read dependencies and validate
  their begin-time generations under exclusive commit admission. Ordinary
  commits take shared admission and remain concurrent; predicate changes and
  write-skew candidates force the stale serializable transaction to retry.
- Native savepoints continue to roll back database writes and broker outbox
  entries together. A failed owning commit consumes its handle, allowing a
  Carrier retry block to start a genuinely fresh transaction.
- A Carrier block cannot silently strengthen an already-active transaction:
  compatible nesting uses a savepoint, while a stronger requested isolation
  fails closed instead of being downgraded. Atomic route-cache, idempotency,
  workflow, and propagated-service wrappers remain read committed until their
  dedicated Carrier parity slices define stronger outer-transaction retry.
- Concurrent compiler-signed model upserts retry the losing unique-key insert
  from a new snapshot and re-evaluate the update branch, matching PostgreSQL
  conflict-update behavior without exposing raw SQL authority.

## Embedded Carrier programs

- Compiler-signed feature-flag definitions evaluate tenant targeting and
  deterministic percentage rollout only from the trusted actor context.
- Capability-aware graph helpers fail closed when no native graph engine is
  available and execute only their signed bounded-SQL fallback statement.
- Direct Carrier jobs bind literal job names to private signed broker queues.
  The generic worker preserves actor context and bounded baggage; immediate,
  delayed, and transaction-buffered publication share the durable broker.
