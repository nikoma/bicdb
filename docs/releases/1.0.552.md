# 1.0.552: EXPLAIN describes the plan that runs, and subqueries are hashed

## Changed

- **EXPLAIN names the scans and joins that actually execute.** The index
  locator, which collects row ids and then fetches the rows, prints as a
  Bitmap Heap Scan over a Bitmap Index Scan (BitmapOr for its OR route).
  Index Scan is printed only where rows really arrive in index order or at
  most one row is read. Joins print in the order the executor runs them, and
  each join's method comes from the executor's own join rules instead of
  always reading Hash Join. The ORDER BY index shown is the one the executor
  uses, not one from the unused cost-based planner. A truth test checks every
  scan, join and subplan label against what was recorded during execution.
- **Subqueries are evaluated once and probed by hash.** An uncorrelated
  `IN (subquery)` runs once per statement and is probed through a hash table.
  A correlated `EXISTS` / `NOT EXISTS` of the form `inner.k = outer.c` reads
  the inner keys once and runs as a Hash Semi Join / Hash Anti Join. Other
  shapes keep the per-row path. Query results are unchanged.

## Fixed

- **`x NOT IN (empty subquery)` returned NULL for a NULL `x`.** It now returns
  true, as the SQL standard requires.
